# Accessible

Turn a crowded, noisy UI into one that is calm, scannable, and professional — without losing any of the information it carries.

**These principles are illustrative starting points, not a fixed visual style or a fixed markup pattern.** No specific font, palette, framework, templating syntax, component shape, or "brand feel" is mandated anywhere in this skill. Every code-shaped illustration in `examples/` is marked as one instance among many (`[bracket notation]` for interchangeable choices) — never copy a class name, component structure, or exact snippet from there into an unrelated project; reason from the structural description instead, expressed in whatever language and styling system the actual input already uses.

## Commands — multi-file entry points, distinct from a normal single-file pass

Everything elsewhere in this skill describes applying one mode to one input and delivering one result. Two commands change that shape: they operate when the person has handed over **a whole project or many pages**, not a single file, and each produces something other than a single finished pass. Both are triggered explicitly — `/accessible taste [n] <mode>` and `/accessible snippet <mode>` — and neither is the default; without one of these keywords, a multi-file input still gets the normal single-pass treatment (pick the most relevant file, or ask which one, same as always).

### `/accessible taste [n] <mode>` — preview N genuinely different directions before committing

**When to use it:** the person is about to apply this skill across a whole project or a large batch of pages, and wants to see real options before the actual rollout commits to one visual direction. `n` defaults to **3** when omitted; the person can name any count (`/accessible taste 4 ultra`, `/accessible taste 2 medium`). The mode (`lite`/`medium`/`ultra`) still works exactly as documented elsewhere — `taste` changes how many directions get built and how they're delivered, not what each direction contains.

**Picking the sample file.** If the person named a specific file, use it. If they haven't, pick the single file from the project that most exercises this mode's moves — for Ultra, that means the file with the most distinct question-types in view at once (the redistribution test from the moves below), since a thin settings page won't show three directions differing from each other in any meaningful way. State which file was picked and why, in one line, before building — don't build silently against a guess.

**What makes N directions genuinely different, not N minor variations.** This is the part most likely to be faked under time pressure — three passes that only differ by accent hue are not three tastes. Each direction should differ on at least one of the large judgment calls named elsewhere in this skill: working-surface light/dark direction, chrome position (side/top/bottom/floating), chrome color (dark-neutral/light-neutral/full-brand-hue), type/spacing scale (comfortable/large/enormous), page-split shape, or overall density philosophy.

**How to actually arrive at `n` directions, not just list the axes they could vary on.** Listing the axes is not the same as picking real values on them — that's a generation method, and it has three steps:

1. **For each judgment-call axis, ask what this specific input's own constraints actually rule in or out** — the same derive-from-constraints method used for a prior-pass re-approach (see `examples/rerun-detection.md`, point 3): look at what the input's own content and structure make plausible, not at what's abstractly possible. A dozen long, non-iconic nav labels rules out icon-first chrome as a serious option; a nav with 4–5 short, visually distinct items makes it a live option. A product whose current identity is fundamentally tied to a saturated color (that color *is* the brand, not just an inherited choice) makes "drop the brand hue entirely" a weak direction, while "concentrate it in chrome vs. spread it across accents" are both live. Don't skip this step and jump straight to picking combinations — an axis with no plausible alternative for this input shouldn't be the thing that varies between two of the `n` directions.
2. **From the axes that do have more than one live option, choose `n` combinations that are each internally coherent, not just individually defensible in isolation.** A direction is a *design*, not a checklist of independently-chosen values — "light working surface + top-bar chrome + comfortable scale" needs to hang together as something a real product could plausibly ship, not just be three technically-valid answers stapled together. If two axes' live options interact (e.g. a very dense, airy Ultra-scale pairs awkwardly with a floating/collapsible chrome panel that itself eats screen space), let that interaction rule out combinations rather than presenting all of them as equally coherent.
3. **Push for real spread across the `n` you pick, not `n` points clustered near the safest option.** If step 1 leaves 3+ live options on 2+ axes, don't default to picking the `n` closest to the original input's own choices — that reproduces the under-delivery failure this command exists to avoid (see the prior-pass check above: minimal restructuring of something already reasoned-through). At least one of the `n` directions should represent a genuinely different overall feel from the input's current one, not a refinement of it, provided step 1 didn't rule that out as implausible for this specific product.

Pick `n` combinations arrived at this way — not the n most extreme combinations for shock value (that fails step 2's coherence test as often as it passes it), and not n small nudges off a single baseline (that fails step 3). State each direction's defining choices in one line (a "tag," in the template below) before building it, so the person can tell at a glance what's actually different about each card, not just discover it by clicking through.

**Spread is bounded by the constraints — it does not override them.** Step 3 pushes across the axes step 1 found *open*. The dwell-time rule (see the palette move below) is a constraint on which axes are open at all, not one more axis to vary for the sake of variety. Concretely: for a product whose high-dwell-time working surface is read for long stretches — a data-dense admin/ops console, a form-heavy business tool, an analytics table — "dark working surface" is usually **not** a live option, and building it anyway to reach a count of n manufactures a direction this skill would reject on a normal single-file pass. Drop it and substitute a different *open* axis instead (chrome position, chrome colour, scale, density philosophy, page-split shape — these stay genuinely open even when the working-surface direction is settled). Note that chrome's colour and the working surface's light/dark are independent axes, so a bold or identity-saturated direction is still fully available to you even when the surface must stay light: a full-brand-hue rail over a light working surface is a real, unconstrained, genuinely-different direction.

**Building and delivering.** Build each direction as its own complete, self-contained file (or small file set) at the requested mode, in full — a taste preview is not a lower-fidelity sketch of the real pass, it's the real pass, done n times with different judgment-call answers. Then load `assets/taste-picker-template.html` as the shell: fill in one `.taste-card` per direction (name, one-line tag stating what's different about it, and the built file as the iframe's source), regenerate the grid to have exactly `n` cards, and publish the picker alongside the built direction files. The picker is the thing the person interacts with; the individual direction files are what it loads.

**The "Use this one" button copies a prompt — it does not, and cannot, message the agent directly.** A published page has no reliable channel back into whatever is running this skill: inside claude.ai the person can just reply in chat, but the same picker page is just as likely to be opened from a CLI-based agent (Claude Code, a terminal-launched build, or anywhere else this skill runs headless) where there is no chat to reply in at all. Design for that harder case, not just the chat case: each card's button copies a ready-to-paste prompt to the clipboard rather than trying to fire an event the agent might not be listening for. Concretely, when filling in the template:
- Write each card's hidden `[data-role="copy-src"]` content as one self-contained sentence or two naming that direction's actual judgment-call answers (chrome position and color, working-surface direction, scale, page-split) — it has to make sense pasted into a brand-new agent turn with zero other context attached, since the person may paste it into a different session than the one that built it. A vague "use direction A" with no restated content copies nothing useful.
- Leave `data-context` unset unless it's already known for certain which surface will render this page — the template's own script guesses chat vs. CLI from whether the page is embedded, and that guess is usually right; only hardcode `data-context="chat"` or `data-context="cli"` on `<body>` when the calling context is unambiguous (e.g. this skill is explicitly being invoked from within Claude Code).
- Don't strip the copy behavior out to simplify the page even when building for claude.ai specifically — a person can still use it there (copy the prompt into a follow-up message instead of retyping their choice), and it costs nothing to leave in.

**After the person picks — whether by replying in chat or by pasting the copied prompt into a fresh agent turn.** Continue from their choice — either treat it as the finished result for that one file (if that's all they needed), or, since `taste` exists specifically for whole-project rollouts, treat the picked direction's judgment-call answers as the standing defaults for the rest of the project and proceed file-by-file without re-litigating the same calls each time, unless the person says a specific later page should diverge. If the pasted prompt arrives with no other context (a fresh CLI session), treat its restated judgment-call answers as sufficient to proceed without asking the person to re-explain what they already chose on the picker page.

### `/accessible snippet <mode>` — prove the direction on one file before touching the rest

**When to use it:** the person has many files (a whole project) and wants to validate a redesign's *feel* on one representative file before committing to rolling it out everywhere — a lower-overhead alternative to `taste` when the person already has a direction in mind and just wants a fast go/no-go loop rather than a side-by-side comparison.

**Picking the sample file.** Same rule as `taste`: use a named file if given one, otherwise pick and state the one that best represents the project's typical complexity — not the simplest file (which won't reveal problems) and not an outlier (which won't represent the rest).

**Mockup-data, no-source-modification rule — this is what makes `snippet` different from a normal single-file pass.** The first round of `snippet` output is always a standalone rendering — real layout, real styling, real structure, built at the requested mode — but populated with representative **mockup data**, and it is never a modification of the actual source file. This holds regardless of source format:
- If the input file is already plain HTML, the snippet is still a *separate* output file, not an edit made in place to the original — the person is looking at a proof, not a live change, until they say otherwise.
- If the input is written in anything else — any component framework, any templating language, any server-rendered format, whatever the actual source happens to be — the snippet extracts and rebuilds that file's *visual shape* as a standalone HTML mockup. It does not edit the source file itself, in its own language, and it does not attempt to preserve or replicate that source's live data-binding, props, state logic, directives, or server-side logic — none of that transfers to a static HTML proof, regardless of which language or framework it was written in. The output is disposable proof-of-concept markup, not a drop-in replacement for the source file. Say this plainly when delivering a snippet from a non-HTML source — name the source's actual format in that sentence, not a generic placeholder — so the person doesn't mistake the mockup for a ready-to-merge component.

**The like/dislike loop.** After delivering one snippet, stop and ask whether it lands, rather than continuing on to the next file unprompted:
- **If liked** — that direction's judgment-call answers (same set named under `taste` above) become the standing default, and the person can then say to proceed to the next file, or to proceed through the rest of the project. When actually rolling out to the remaining files, that later work *does* modify the real source files in the normal way this skill always has — the mockup-data/no-modification rule is specific to the first proving round, not to the whole command.
- **If disliked** — ask what's off (or take a specific redirect if they already gave one) and rebuild the same sample file's snippet with the new direction, still as mockup data, still not touching source — don't move on to another file until the current one lands or the person says to stop iterating and move on anyway.

`taste` and `snippet` solve the same underlying problem (don't commit a whole project to one direction sight-unseen) from two different angles — `taste` shows several options at once for a side-by-side choice, `snippet` iterates on one option at a time for a faster yes/no loop. Use whichever the person's request matches; if they ask for one by name, that's what they get, without substituting the other because it seems more efficient.

## Modes — always required, always explicit

This skill has three intensities. **Always determine which one applies before doing any work; if the person hasn't said, ask which mode they want rather than picking one.** A short one-line description of the three is enough for them to choose from — don't over-explain.

- **Lite** — typography, spacing, visual encoding, and micro-polish, all applied *in place*. Layout regions, page count, and navigation stay exactly as they are — nothing relocates to a new section or a new page, and no new pages get created. Small structural additions are allowed when they replace something already there without moving it elsewhere (a run-on stat string becoming a bar-plus-legend in the same cell; a warning that was squeezed into a cell becoming its own sub-block still inside that same row) — what stays fixed is *where on the page* each piece of content lives, not whether its markup can grow slightly to render better. **Output: always a single file/page.**
- **Medium** — everything in Lite, plus redistributing and relocating content within the same page: data can move into new visual forms (bars, callouts, summaries), rows/cards can be restructured internally, warnings can be pulled out into their own summary zone. Same overall brand feeling and same broad color direction, but internal layout is fair game. (Moves 1–4, 5, 6, 7, 9, 11, 12.) **Output: usually still a single file/page** — splitting into a second page is a genuine judgment call at this mode, made only when the content has clearly outgrown one page's hierarchy (see the redistribution move below for the test), not a default outcome. If in doubt at Medium, stay on one page.
- **Ultra** — everything in Medium, plus full re-theming: new color schema, new visual language, complete re-layout, re-structuring at every level. (All 12 moves, taken as far as they go — see the Ultra section below.) **Output: expect and default to multiple files/pages** — a real Ultra-grade transformation of a data-dense screen splits the aggregate/summary questions (health, trend, comparison, composition) onto their own page (an "Overview," a dashboard) distinct from the detail list/table page, the way a genuine from-scratch redesign would ship it, not as a single long page with better-organized sections. Staying single-page at Ultra is the exception, not the default — only justified when the content is genuinely too simple to warrant a second page (a short settings form, a single focused tool), and that justification should be stated explicitly rather than assumed. **If a request calls itself Ultra but the actual output stays single-page with only in-page reorganization and a new palette, that is a Medium-grade result mislabeled Ultra — catch this before delivering, not after.**

Where "page" is used above, treat it as whatever the actual output format's equivalent is — a second file, a second route/screen in a component-based app, a second tab/panel in a design tool — not literally a second `.html` file specifically.

See `examples/mode-lite-fullpass.md`, `examples/mode-medium-fullpass.md`, and `examples/mode-ultra-fullpass.md` for what a complete pass at each of these three actually looks like assembled together, not just move-by-move.

Once the mode is confirmed, don't re-ask or hedge mid-task — proceed for the whole request at that intensity. If the person asks for a specific mode, that is sufficient authorization to make the changes that mode implies (including, in Ultra, adding new pages or restructuring navigation) without pausing for a second confirmation.

### Ultra pushes for maximum accessibility, but consults on judgment calls that affect it

Ultra's mandate is to push readability and calm as far as they genuinely go, not to settle for whatever change is smallest or safest-looking. Several individual moves at Ultra involve a real judgment call with more than one defensible answer — the working-surface light/dark direction (palette move above) is one, chrome's position and chrome's color (side/top/bottom/floating; dark-neutral, light-neutral, or full brand-hue) are others, and the same applies to other Ultra-only decisions with a comparably large effect on the result (e.g. how aggressively to collapse pages, how far to push a from-scratch visual language versus staying close to the original's specific look). Two failure modes to avoid here, and they pull in opposite directions:

- **Silently defaulting to the least-changed option** because it's the safe-looking middle ground (e.g. "keep it dark, just softer" without ever seriously evaluating light) — Ultra explicitly does not reward staying close to the original when a bigger change would genuinely read better and more accessible.
- **Silently deciding a big, consequential judgment call on the person's behalf** without surfacing it, when the person would reasonably want a say (a fundamentally different visual direction, not just an execution detail).

Resolve this by: forming a genuine recommendation from what the input itself signals (a dark-context media/creative tool's own before-state is real evidence it should probably stay dark; a dense all-dark admin/data console is real evidence its working surface would likely read better breaking away from dark, since dark-everywhere in that kind of tool is usually an unexamined default, not an intentional identity choice) — then, for the judgment calls with the largest effect on the outcome, state the recommendation and proceed with it as the default, while explicitly inviting a quick correction if the person has a different preference, rather than either asking a blocking question or deciding silently with no visibility into the call that was made.

The same treatment applies to **how large the type/spacing scale itself goes** (see the typography move below for the comfortable/large/enormous spectrum) — at Ultra this compounds with every other move (a bigger type scale plus a multi-page split plus a rebuilt palette is a much bigger combined change than any one alone), so it's one of the judgment calls to name explicitly rather than default through silently.

### Before diagnosing: check whether this input is already a prior accessible pass

The "crowded, noisy" diagnosis below assumes the input is an unexamined original. That assumption can be wrong, and silently proceeding as if it's always right produces a specific bad outcome: applying only small, incremental tweaks to something that's already well-structured, when what's actually needed is a real report back to the person that there isn't much crowding left to fix by the usual moves — and, separately, an offer to explore a *different structural direction or taste*, not a bigger dose of the same one. See `examples/rerun-detection.md` for this reasoned through on a full input, including where a generic-signals check is not enough on its own.

**Check the session's own history first — this is the most reliable signal and comes before anything else.** If this skill (or an equivalent redesign pass) already ran earlier in this same conversation, the input may *be* — in whole or in part — Claude's own prior output, even if it arrives as a fresh upload, a different filename, or only one file of a multi-file result the person isn't re-sharing in full. Before reasoning from generic signals, check: does any file, page, or section handed in now match, resemble, or plausibly descend from something already built earlier in this conversation? A page named "overview" appearing right after an Ultra pass built an "overview" page as its aggregate/dashboard page is not a coincidence needing generic-signal confirmation — it's the same artifact, and should be recognized as such directly. Don't wait to independently re-derive "this looks polished" from scratch when the conversation itself already answers whether it's prior output.

**Absent that, or in addition to it, recognize a prior pass from the input's own shape.** Signals include: a deliberate multi-step tonal ramp rather than ad-hoc colors, generous type/spacing already in place, content already redistributed onto a dashboard/overview separate from a detail page, promoted warning blocks, real depth/elevation, a consistent icon system — in short, the output shape this skill itself produces. Treat this as a real check to make on the actual input, not a formality to gesture at.

**When recognized, stop and report before building anything:**
1. Say plainly that the input already looks like it's been through an accessible-style pass (name the specific evidence — the ramp, the redistribution, the elevation system, or "this is the file I built earlier in this conversation" when that's what it is — briefly, don't just assert it).
2. Don't default to hunting for small residual crowding issues and patching them — that produces exactly the minimal-restructure, minimal-redesign outcome that under-delivers on a fresh request. If the mode requested is Ultra or Medium and the input is already clean, there usually isn't a "make it less crowded" job left to do in the usual sense.
3. Instead, explicitly offer to reapproach it from a **different structural direction or visual taste** — genuinely different choices, not a bigger version of the same ones already made. **Derive the options from this specific input, not from a stock list**: look at what's actually fixed about the current design (nav position, icon-vs-text density, card vs. list paradigm, tonal direction, information density) and for each, name the realistic alternative this particular product could take — a side-rail nav could become a top bar or a collapsible sliding panel *if* the input's own chrome-to-content ratio and navigation depth make that plausible; a text-label nav could go icon-first *if* the nav items are few enough and recognizable enough as icons; a warm/cool tonal direction could flip *if* the product's identity doesn't depend on the current one. Offering an alternative that doesn't fit this input's actual constraints (e.g. proposing icon-only nav for a screen with a dozen long, non-obvious nav labels) is worse than not offering one — it signals the options weren't actually derived from what's there. Ask which direction, if any, they want explored — this is a real fork in the work, not a detail to bury in the build.
4. Only proceed straight into a build without this stop-and-report if the person's own request already answers it — they named a specific new direction, said explicitly they know it's already been through a pass and want more of the same anyway, or said to just proceed.

**This interacts with mode selection (workflow step 1), not just diagnosis.** Asking "which mode — Lite, Medium, or Ultra" to a person whose input already went through an Ultra pass is a different question than asking it of someone with a genuinely crowded original — the honest framing at that point is closer to "this already got a full pass; do you want a lighter refinement, or a genuinely different take at the same intensity," and the direction-offer above is what fills in what "a genuinely different take" could mean. Fold the two together in one message rather than asking about mode first and surfacing the prior-pass finding as a separate, later interruption.

This check is separate from, and comes before, the type/spacing re-run note above — that note covers what to do about *scale* specifically once work is already underway; this one covers whether to stop and reframe the whole request before starting.


## Read this first: what "crowded" actually means

Before touching any code, diagnose the specific failures present, regardless of mode — this becomes the plan, scoped to whichever moves the chosen mode allows:

1. **Flat information hierarchy.** Everything sits at the same visual weight and zoom level, forcing the user to *read* to find what matters instead of *glancing*. (Medium/Ultra to fully fix; Lite can only fix this partially, via weight/size, not relocation.)
2. **Text standing in for visual encoding.** Proportions, statuses, or trends expressed as run-on strings instead of shapes, bars, or color.
3. **Inline overflow.** Warnings or secondary metadata crammed into the same cell/line/card as the primary content instead of given their own space.
4. **Undifferentiated repetition.** Many small same-weight elements (tags, pills, icons, buttons) with no grouping or priority.
5. **Harsh, cramped typography and spacing.** Small type, tight line-height, minimal padding, extreme contrast that's fatiguing over sustained reading. Note this failure runs in **both directions**: too little contrast is illegible, and too *much* — near-white text on a near-black ground, or high-chroma colour glowing on black — is just as fatiguing, and is precisely what a check that only tests a contrast *minimum* waves straight through. See "Comfort ceilings" below.
6. **No fixed zones for action.** Interactive controls scattered rather than living in predictable places.
7. **Flat depth.** Every surface on one plane with thin borders as the only separator.
8. **Chart-junk.** Charts carry decoration rather than legible signal.
9. **Placeholder-style icons.** Ad-hoc text glyphs or emoji standing in for icons.
10. **Name/content mismatch.** A heading, label, page title, or section name makes an implicit promise about what the reader will find there — "Overview" or "Summary" promises quick, low-complexity, at-a-glance content; "Details" or a table's own column headers promise the opposite; "Quick actions" promises a small number of fast, low-friction controls. When the actual content under that name breaks its promise — an "Overview" page that's actually a dense data table, a "Summary" that runs longer and more granular than the thing it's supposedly summarizing, "Quick actions" with a dozen multi-step controls — that's a distinct failure from visual crowding. The layout can be flawless and the mismatch still misleads the reader about what kind of engagement the section asks of them before they've read a word of it.

## The transformation moves, by mode

Each move below is tagged with the lowest mode it belongs to; every mode includes all moves tagged at or below its own level.

### [Lite+] Open up typography and spacing
Increase base type size and line-height for anything read continuously, and give elements enough internal padding to breathe. Headings get real weight and, usually, slightly tightened letter-spacing. **In Lite, this is the primary move** — it should visibly transform the feel of the screen through type/spacing/weight alone, without touching layout, adding regions, or changing what's a pill vs. plain text. Push it further than feels natural for "just a font change": larger jumps in size and padding than a first instinct suggests are what make a Lite pass actually register as a real improvement rather than a barely-noticeable tweak.

**But "how much bigger" is a real judgment call, not a one-size answer — surface it rather than picking silently.** The right scale depends on the surface: a dense data-console table read for minutes at a stretch wants a smaller jump than a marketing page or a single-focus form. There's also a ceiling most people don't expect: past a certain point, "bigger" stops reading as "more comfortable" and starts costing scannability — a data-dense screen with everything blown up forces more scrolling and more eye travel per fact, which is its own kind of fatigue. So:

- If the person hasn't specified, state the scale you're defaulting to in one line before or alongside the pass (e.g. "opening up type/spacing by roughly 10–15% — say if you want it larger or to leave it closer to the original") rather than silently picking a number and moving on.
- If the person's own words carry an intensity signal ("comfortable," "a bit more breathing room" vs. "huge," "enormous," "can't strain to read it") or a scale reference (a specific point size, "like a book," "like a phone settings screen"), take that as the target and say so, rather than defaulting to a fixed percentage regardless of what they asked for.
- If they ask for something in comfortable/large/enormous terms without a number, treat it as a spectrum and pick a concrete point on it, named out loud: *comfortable* ≈ a restrained bump mainly to line-height/padding with type size barely moving; *large* ≈ a clearly noticeable size increase across the board, still dense-content-safe; *enormous* ≈ near accessibility/low-vision scale, where density itself may need to drop (fewer columns, more relocation) to keep the result scannable rather than just zoomed-in. Naming which of these (or where between them) you're building is more useful to them than a bare percentage.
- Rerunning this skill on a screen that already went through an accessible pass is a signal worth naming, not silently compounding: if the input already shows the hallmarks of a prior pass (a deliberate tonal ramp, generous padding, a redistributed dashboard), say so and ask whether this round should push the scale further, hold it steady and focus on other moves, or pull back — rather than treating it as a fresh crowded screen and stacking another full size increase on top.

### [Lite+] Replace concatenated-text stats with visual encoding
Any run-on stat string becomes a small proportional visual (segmented bar, ring, sparkline) plus a compact legend, in place, without moving where that stat lives on the screen. Keep the color-to-meaning mapping consistent across the whole UI.

### [Lite+] Promote inline warnings/errors to their own block
A warning crammed into a cell becomes a full-width callout: icon, bold headline claim, one plain-language sentence, a clear action. This can happen at Lite scoped to *within* the same row/unit (the warning gets its own full-width sub-block right where it was) — moving it to an entirely different section of the page, or a different page, is a Medium-level relocation (see move 1).

### [Lite+] Give actions fixed, predictable zones
Within each existing row/card/header, arrange its own actions into one consistent trailing cluster instead of scattering them — this is a local rearrangement inside a unit that already exists, not a relocation across units. Introducing a *new* shared zone that pulls actions together from multiple different rows or sections (e.g. a floating bulk-action bar that didn't exist before) is a Medium-level addition, since it changes the page's structure, not just one unit's internal order.

### [Lite+] Charts carry only what answers their question — no chart-junk
Cut any chart element that doesn't answer a specific reading — this applies even to charts that already exist in the input; a chart's own excess decoration can be trimmed without relocating the chart itself.

### [Lite+] Use a real icon system where it earns its cost
Convert identity-defining, always-visible chrome icons (nav, brand mark) to a proper icon system; be pragmatic about small repeated low-emphasis glyphs elsewhere — in place, without adding new icons or new navigation.

### [Medium+] Redistribute the same data into multiple projections, not multiple copies
List every distinct question the crowded view is forced to answer at once (e.g. "is everything OK," "what's the trend," "how do items compare," "what's the composition," "which item needs action, and why"). Give each question its own purpose-built projection of the *same* data — a summary metric, a trend visualization, a comparison view, a composition view, a detail row — rather than repeating full detail everywhere. This is the move that most determines whether a redesign reduces noise or just restyles it.

**At Medium**, these projections usually live in new sections of the same page (in-page redistribution, per the mode definition above) — only extract a genuinely new page when this page's content has clearly outgrown one page's hierarchy, and treat that as the exception, not the default. **At Ultra**, default to actually extracting the aggregate-question projections (health, trend, comparison, composition) onto their own new page, distinct from the page that keeps the detail list/table — a single long page with nicely reorganized in-page sections is not, by itself, a complete Ultra outcome, even if the palette and layout within that one page changed completely. The test either mode should apply before finalizing: if this page currently tries to answer more than roughly 2 of the listed questions on its own, at Ultra that's a strong signal a second page is warranted, not just a second in-page section.

### [Medium+] Give every row/card exactly one job
Audit each repeating unit: how many distinct things is it telling the user at once? After redistribution, most units should carry 1–2 responsibilities, each in its own clear slot — this typically requires restructuring the unit's internal layout, which is why it's Medium rather than Lite.

### [Medium+] Fold non-scanned values into plain text; keep scanned values distinct
Ask, per value: scanned across many rows, or only confirmed within one? Scanned values stay distinct objects; confirmed values collapse into plain text. This changes what markup/components exist, not just their styling, so it's Medium.

### [Medium+] Split into zoom levels, sized to content
Lay out redistributed projections (move above) as distinct zones — glance → context → detail — sized to what each region's content actually needs, not forced into a uniform grid. A new shared action surface that spans multiple rows/units (a floating bulk-select bar, a consolidated toolbar pulling controls together from previously-scattered locations) belongs here too — it's a new structural region, not a within-unit rearrangement.

### [Ultra only] Rebuild the palette as a tonal ramp, weighted by dwell time
Replace the existing color system (not just soften individual values) with a deliberate tonal ramp (2–4 steps, one consistent temperature/undertone) plus a status-color system (ink + soft-background pairs), assigned **per region by where the user's attention actually accumulates** — not by mechanically reusing the input's own current color scheme. This is Ultra-only because it's a genuine re-theme: every surface's color role gets reconsidered, not adjusted.

Judge the working surface's direction from what the product actually is, inferable from the source itself (a media/video tool, a creative/dark-context app, or anything whose own before-state signals darkness is core to its identity, not just an unexamined default → can legitimately stay dark, softened; a data-dense admin/ops console, a form-heavy business tool, anything meant for long analytical reading sessions → the strong default is to break away from all-dark and give the high-dwell-time working surface the light, low-fatigue treatment, even if the rest of the product's chrome stays a different, bolder treatment). Don't default to "keep it dark, just softer" as a safe middle ground without doing this judgment explicitly — that's the one outcome most likely to be a missed opportunity rather than a genuine call, because it changes the least and *looks* like a decision was made.

**Chrome — the low-dwell-time region carrying nav and brand — is its own set of independent judgment calls, not a fixed "dark sidebar" default.** Three separate questions, each genuinely open:
- **Where does it live?** A side rail is one instance, not the rule — a top bar, a bottom bar (mobile), a floating/collapsible panel, or chrome that changes position between breakpoints are equally valid depending on what the product's navigation depth and screen proportions actually call for. Don't reach for "sidebar" reflexively; ask where this specific product's nav actually belongs.
- **What color is it?** The brand's identity color doesn't have to be reduced to "a dark neutral with a colored accent" — chrome can legitimately be painted in the brand's actual hue as its dominant surface color (a full brand-green chrome, not dark-gray-with-a-green-highlight), precisely because it's glanced at rather than read continuously, so saturation there doesn't cost the fatigue it would on the working surface. Dark neutral, light neutral, and full-brand-hue are three genuinely different options — pick from evidence about what fits the brand, not by default to whichever is safest.
- **Does its color relate to the working surface's light/dark direction at all?** These are independent axes, not one decision — chrome can be a saturated brand color while the working surface is light, or dark-neutral while the working surface is light, or any other combination; the working-surface call above doesn't predetermine chrome's answer, and chrome's color doesn't predetermine the working surface's.

See `references/principles.md` for the full reasoning and `examples/dwell-time-palette.md` for the structural pattern, including how chrome position and chrome color get reasoned through as separate calls from the working-surface direction.

### [Ultra only] Add real depth
Give grouped surfaces a deliberate shadow and generous corner radius system, replacing flat 1px-border-only separation everywhere at once, reinforced by the new tonal ramp above. A Lite/Medium pass can nudge existing shadows/radii; Ultra is where a full elevation system gets designed from scratch.

### [Ultra only] Split into a real multi-page product, not a longer single page
Default to producing more than one output file/page (roughly the expected outcome ~85% of the time a data-dense screen goes through Ultra) — an "Overview"/dashboard page carrying the redistributed aggregate projections (health, trend, comparison, composition), separate and linked from a "detail" page carrying the actual list/table, mirroring how a real product would ship this rather than how a single file can be reorganized to feel like it. Before calling an Ultra pass complete, check: did the output stay a single file/page with only in-page sections, a new palette, and reorganized layout? If so, that is a Medium-grade result — the palette and layout moves happened, but the structural move that defines Ultra didn't. Go back and extract the aggregate page before delivering. The single-page exception is narrow: genuinely simple content (a short form, one focused tool, a screen with only 1–2 of the redistribution questions to answer at all) can legitimately stay single-page even at Ultra — state that reasoning explicitly when it applies, rather than defaulting to single-page silently.

**Naming the split page(s) creates the exact risk failure mode 10 describes — check the name actually earns its promise before shipping it.** Calling a new page "Overview" is only correct if what actually lands on it reads as quick, low-complexity, at-a-glance — genuine aggregate signals (health, composition, trend, "what needs attention") kept light: a handful of stat cards, a couple of charts, a short action list. If redistributing the original content still leaves that page carrying a dense table, many-column comparisons, or per-row granular detail, "Overview" is now mislabeling what's actually a second detail-grade page — the split happened, but the promise the name makes wasn't honored by what got put under it. This applies to every name introduced or kept through the pass, not just an "Overview" page: a "Summary" section that's longer and more granular than the content it summarizes, "Quick actions" hiding a dozen multi-step controls, a "Details" tab that's actually sparser than the "Overview" next to it — all the same failure, name promising one thing and content delivering another.

## Naming and content must match — check this at every mode, not just Ultra

This is failure mode 10, and unlike the numbered moves above, it isn't something a mode unlocks — it's a check to run regardless of mode, because a mislabeled heading is just as misleading in a Lite pass that never touches structure as it is in an Ultra pass that invents new pages. Two situations, handled differently:

**The input already has the mismatch (Claude didn't create it).** Notice it as part of looking at the actual input (workflow step 2) — read section/page names against what's actually under them, not just at layout/density. When a name's promise doesn't match its content, this is worth surfacing to the person even though it's not strictly a visual-crowding problem this skill was asked to fix: name the specific mismatch in one line ("this page is titled 'Overview' but the content is a full data table with per-row detail — want me to keep the name as-is, retitle it to something that matches what's actually there, or split it so the aggregate view and the detail view are separate?") and let them decide, rather than either silently relabeling something they may have named intentionally (an internal tool's "Overview" might just be established team vocabulary, not a mistake) or silently leaving a misleading label in place because renaming wasn't explicitly requested. This is a genuine consult, not a rhetorical one — proceed with whichever of the offered paths the person picks, and if they don't respond to the callout, default to leaving the name as-is rather than guessing which fix they'd have wanted.

**A move in this pass would create the mismatch (Ultra's page-split is the main case, but any mode can introduce a new heading or section name).** Don't create it in the first place — check the fit as part of the same step that decides the name, the way the page-split move above now does explicitly. This is prevention, not detection-after-the-fact, and it doesn't need a consult, since Claude is the one choosing the name and can just choose one that fits what it's putting under it.

Either way, the underlying judgment is the same: does this name, read cold with no other context, correctly set expectations for the density and complexity of what follows? If not, that's the mismatch to catch.

## Comfort ceilings — the checks that run the other way

Every "make it more accessible" instinct in this skill pushes a value *up*: bigger type, more padding, more contrast, more separation. Each of those has a ceiling past which it starts causing the harm it was meant to fix, and a check that only tests a minimum cannot see it. The type scale already has one (see the typography move: past *enormous*, density itself has to drop). These are the others.

**Contrast is a range, not a floor.** WCAG AA specifies a *minimum*; it is entirely silent about the maximum, which is why "every pairing passes AA" is not evidence that a screen is comfortable. Near-white text on a near-black ground reaches 15–17:1 and reads as harsh, buzzing edges to a large share of readers — the text bleeds outward (halation) rather than sitting crisply, and it is especially painful for people with astigmatism or light sensitivity, and over a long session for everyone else. Rough working targets, for text that is actually *read* for more than a moment:

- **Light working surface:** body text ~7:1 to ~13:1. Soften the ground off pure white and the ink off pure black rather than running both to the extreme.
- **Dark working surface:** cap body text around 12–13:1 — use an off-white ink, not `#fff`. Then desaturate status and accent colours and lift them slightly *toward* the surface instead of placing full-chroma mid-luminance hues on black, which is the second-halation mechanism after raw contrast. Short-wavelength hues (blue, violet, cyan) glow hardest on dark grounds; they belong in small doses there, not as body-colour.
- **Large display numerals and headings** are read for a moment, not tracked across a paragraph, so high contrast on them is fine. The ceiling applies to sustained text — table cells, labels, body copy, anything a user scans down a long list.

**Chrome is exempt from the ceiling, and that exemption is the point of the dwell-time split.** A saturated brand-hue rail or top bar is glanced at, not read, so it can carry contrast and chroma the working surface cannot. When measuring, scope the chrome region out rather than softening it — the fix for a harsh screen is almost never "make the bold region quieter," it is "make the *read* region quieter."

**Page length has a ceiling too.** Scrolling is a physical cost and a comprehension cost: past a few screens a reader loses track of where they were, and content below the fold is content that does not exist for a fraction of users. But long is not automatically wrong — **a page that is long because a paginated data table has many rows is fine; a page that is long because a dozen summary blocks are stacked is the redistribution move failing to happen.** Judge by attributing the height first. The specific failure is the *unbroken run*: several screens of content with no heading, section boundary or sticky orientation to re-anchor on. That, not raw screen count, is what makes a long page inaccessible. If an Ultra pass leaves the detail page longer than the input's, the split did not go far enough — moving the aggregate to its own page should shorten the remaining page, not merely reorganise it.

**Density has a ceiling too.** Opening up spacing reduces how much is visible per screenful; on a table someone compares across many rows, past a certain point every additional pixel of padding costs scrolling and eye travel, which is its own fatigue. The measurable symptom is ink coverage climbing while median block gap stays flat or drops — more air in one dimension, less in the other, net worse.

These are the failure modes `scripts/accessible-audit.mjs` measures. It exists because reading your own output is not the same as measuring it: a palette can look calm, pass AA on every pairing, and still be the one a person says "that hurts my eyes" about.

## Preservation, at every mode

- **Every data point**, always. Reorganized or re-projected, never dropped, at any mode.
- **All interactive affordances** and their underlying behavior/semantics, at any mode.
- **Content and copy**, except where the original text itself was the noise (collapsing tags, rewriting a jargon-heavy warning) — never reworded to change meaning, at any mode.
- **Brand and visual identity, and "the same website" feeling** — this is the one requirement that spans all three modes including Ultra: a returning user should recognize the product. Ultra can change literally every hex value, every layout, every page count, and still satisfy this by keeping the name, the logo/wordmark, the core navigation vocabulary, and the general spirit of the original identity color intact somewhere prominent (concentrated per the dwell-time move above, not necessarily used the same way as before).

## Verify by rendering — mandatory feedback loop, every mode

Reading the markup you just wrote is not verification. Layout, clipping, and colour only resolve in a browser, and a design can satisfy every rule in this skill on paper while still rendering badly. So: **no pass is delivered until it has been rendered, measured, looked at, and re-checked.** This applies to every `taste` direction individually, not just to a single-file pass — an unrendered direction card shown to a person is an unverified claim.

Run the loop, not a single check:

1. **Render and measure.** `node scripts/accessible-audit.mjs <file-or-url> --out report.json --shot render.png` (headless Chrome over CDP, no npm dependencies; pass `--chrome /path/to/chrome` if it can't find one). It reports contrast floor *and* ceiling violations, halation candidates, ink-coverage/whitespace ratio, per-region density, focus ranking and hierarchy spread, saturated-accent load, type scale, undersized hit targets, clipped/overflowing elements, and page length with its unbroken-run measure. Exit code 0 means clean.

   **For measured rather than declared contrast**, run `node scripts/accessible-contrast.mjs <file>`. The audit computes a text run's background by walking the DOM and compositing colour values, which is an approximation that breaks on the cases that matter: text over a **gradient** (one ratio per run is a fiction — the string's two ends sit on different colours), over images or canvas, under translucent overlays, and near `backdrop-filter`. That script screenshots the page, decodes the PNG, and samples the surface pixels actually around each run, reporting `inner` (against the dominant measured backdrop) and `worst` (the nearest-luminance surface pixel). A run can pass `inner` and fail `worst`; that gap is the hidden failure, and no computed-style checker can see it.

   **For a single comparable number**, run `node scripts/accessible-score.mjs <file.html ...>`, which consumes the same audit and ranks several pages against each other across five weighted dimensions — legibility 22%, comfort 24%, hierarchy 20%, length 24%, robustness 10% — with a letter grade. Two properties of it matter more than the number:
   - **Gates dominate points.** A page with a WCAG floor violation, halation on the reading surface, or clipped content cannot average its way into the top band with generous padding; it is capped and labelled, however high its other dimensions run. Comfort-ceiling and systemic target failures cap less severely. This is deliberate — a composite that lets legibility be traded against whitespace is measuring the wrong thing.
   - **`--exclude` marks low-dwell chrome and is exempt from the *ceiling* only.** A saturated brand-hue rail may be loud; its text still has to be readable. Passing `--exclude` and having it suppress floor checks too would hide exactly the failures chrome tends to contain.
   - Rank pages against each other with it; do not read "84 vs 88" as a meaningful gap. The weights are calibrated on a handful of human judgements, not a corpus.
2. **Actually look at `render.png`.** Do not skip this and trust the numbers. The script cannot see a fund-code chip whose text spills into the name beside it, a filter row that wrapped and left dead space, a sticky bar sitting over the last row's content, a column that lost its alignment, or a heading that reads as decoration rather than structure. Those are the failures people notice first. Look at the image and name what's wrong with it, in your own words, before declaring the numbers sufficient.
3. **Answer the mode checklist against what you saw**, item by item, pass or fail — not a summary sentence claiming you checked.
4. **Fix, re-render, re-check.** Repeat until clean. After three loops without converging, stop and report honestly which items remain unmet and why, rather than quietly delivering.
5. **Compare numerically against a reference** when one exists: `--baseline reference.json` prints a delta per metric. If the person has already approved an output as "this is what I want", audit that file once, keep its report, and use it as the baseline for everything after — it turns "is this as good as the one I liked?" into a number.

**Mode checklist.**

*Lite* — every diagnosed crowding item addressed within the moves Lite permits; type/spacing visibly opened relative to the input (measure the median font size and block gap against the original, don't eyeball it); no layout region moved, no page added, no navigation changed; nothing dropped.

*Medium* — everything in Lite, plus: each question from the redistribution list has its own projection; the detail unit now carries measurably fewer distinct facts per row than the input did (if the count is unchanged, the data was restyled, not redistributed — see `references/principles.md`); one job per unit; non-scanned values folded to plain text; new shared action surfaces are in predictable fixed positions.

*Ultra* — everything in Medium, plus: output is multiple pages/files or the single-page exception is stated in one sentence; token layer rebuilt as a tonal ramp; real elevation system; every stat/filter/action from the source still present somewhere; brand still recognisable; each page's *name* matches the density of what landed under it; the working-surface light/dark call from step 5 was actually applied and not quietly reverted mid-build.

*Every mode* — the comfort ceilings: no sustained-text pairing above the ceiling, no high-chroma colour on a near-black working surface, no unbroken multi-screen run without a structural signpost, form controls and buttons at least 24px (44px comfortable), nothing clipped, no page-level horizontal overflow. Small *text links* in breadcrumbs, nav and prose are exempt — advisory, not failures, and treating them as breaches hides the real ones.

**Two traps specific to this step.**

*A passing contrast check is not proof of comfort.* WCAG is a floor. If the script reports zero AA violations, that says nothing about the ceiling — read the ceiling and halation counts too, and treat "AA clean, ceiling dirty" as a failure, not a wash.

*If you write or adapt any colour-measuring code, resolve colours by rasterizing.* Browsers hand back `oklch()`, `oklab()`, `lab()`, `lch()`, `color-mix()` and `color()` **exactly as authored** in computed styles — and canvas `fillStyle` echoes them back too, so neither string-parsing nor reading `fillStyle` works. Paint a 1px rect and read the pixel with `getImageData`. A checker that silently fails to parse these reports zero violations on every modern palette, which is worse than no checker at all because it looks like a pass. `scripts/accessible-audit.mjs` handles this; if you hand-roll anything, handle it too.

When the output is not renderable HTML — a React/Vue/Svelte component, a native screen, a design file — render whatever you can (dev server, screenshot of the running app, exported image) and inspect that. If genuinely nothing can be rendered, say so explicitly in the delivery rather than implying the visual check happened.

## Workflow

1. **Determine the mode.** If not stated, ask — don't guess and don't default silently.
2. **Look at the actual input** — view/read files fully, or examine a screenshot closely for actual font sizes, spacing, and color relationships. Reuse and extend any existing design tokens/system, except in Ultra, where the token layer itself is being rebuilt. **As part of this same look, read every section/page name against what's actually under it** (failure mode 10, below) — a mismatch found here gets surfaced to the person as its own callout before proceeding, independent of whatever mode-based work follows.
3. **Check whether the input is already a prior accessible-style pass** — check this conversation's own earlier outputs first, then the input's own shape (see the check above and `examples/rerun-detection.md`). If it is, stop here and report that back with the specific evidence, then offer a different structural direction/taste derived from this input's actual constraints — rather than proceeding to diagnose it as freshly crowded — unless the person's request already specifies a new direction or explicitly wants more of the same.
4. **Diagnose** using the failure modes above; state briefly which apply and which the chosen mode will actually address (Lite legitimately leaves some diagnosed problems unfixed — say so rather than quietly under-delivering or over-reaching past the requested mode).
5. **At Ultra**, before building anything, name the judgment calls with the largest effect on the outcome (working-surface light/dark direction; chrome's position — side/top/bottom/floating; chrome's color — dark-neutral, light-neutral, or full brand-hue; single- vs. multi-page split; how far to depart from the original's specific look; how large the type/spacing scale goes — comfortable vs. large vs. enormous) — form a recommendation for each from what the input itself signals, state it plainly, and proceed with it as the default while inviting a quick correction, rather than silently picking the least-changed option or silently deciding on the person's behalf.
6. **At Medium/Ultra**, list the questions the crowded view answers at once (redistribution move) before writing any markup. **At Ultra specifically**, this is where the single-page-vs-multi-page call from step 5 gets applied — don't let it happen implicitly by just seeing how much fits on one page once built.
7. **At Medium/Ultra**, audit for one-job-per-unit across the planned rows/cards.
8. **Build or extend the token layer** (color ramp at Ultra; spacing/type scale at every mode) before touching component markup.
9. **Rebuild region by region**, applying the moves the chosen mode includes. **At Ultra**, this means building the separate pages/files decided at step 6, not one file with more sections.
10. **Check preservation**: every stat, link, and control still present; brand still recognizable.
11. **Run the render-verify loop** (see "Verify by rendering" above) — render it, measure it with `scripts/accessible-audit.mjs`, *look at the screenshot*, answer the mode checklist item by item, fix, repeat until clean. Contrast is checked in both directions here: WCAG AA minimum on every text/background pairing **and** the comfort ceiling on sustained text (see "Comfort ceilings"). Hit targets comfortably tappable/clickable.
12. **At Ultra, before delivering**: confirm the output is actually multiple files/pages, or that the single-page exception was deliberately chosen and can be stated in one sentence. An Ultra result that's a single file with a new palette and reorganized sections is a Medium result — catch this here, not after delivering it as Ultra. Also confirm the working-surface light/dark call from step 5 was actually applied, not quietly reverted to "same as before, just softer" during the build. Also confirm any name introduced by the split (an "Overview," a "Summary," etc.) actually matches what landed under it — check this the same way step 2 checked the original input's names, since a newly-created page is just as capable of earning a mismatch as an inherited one. **Every item in this step must be confirmed against a rendered screenshot you actually looked at, not against the markup you intended to write** — and the audit's ceiling and halation counts must be zero on the working surface (chrome regions scoped out with `--exclude` where they are legitimately bold). If you cannot state what the render showed you, you have not verified it; say so rather than implying you did.
