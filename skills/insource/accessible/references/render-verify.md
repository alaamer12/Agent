# The render-verify loop, in full

`SKILL.md` states the loop as a gate; this is what each step actually checks and the traps that made them necessary.

## Verify by rendering — mandatory feedback loop, every mode

Reading the markup you just wrote is not verification. Layout, clipping, and colour only resolve in a browser, and a design can satisfy every rule in this skill on paper while still rendering badly. So: **no pass is delivered until it has been rendered, measured, looked at, and re-checked.** This applies to every `taste` direction individually, not just to a single-file pass — an unrendered direction card shown to a person is an unverified claim.

Run the loop, not a single check:

1. **Render and measure.** `node scripts/accessible-audit.mjs <file-or-url> --out report.json --shot render.png` (headless Chrome over CDP, no npm dependencies; pass `--chrome /path/to/chrome` if it can't find one). It reports contrast floor *and* ceiling violations, halation candidates, ink-coverage/whitespace ratio, per-region density, focus ranking and hierarchy spread, saturated-accent load, type scale, undersized hit targets, clipped/overflowing elements, and page length with its unbroken-run measure. Exit code 0 means clean.

   **For measured rather than declared contrast**, run `node scripts/accessible-contrast.mjs <file>`. The audit computes a text run's background by walking the DOM and compositing colour values, which is an approximation that breaks on the cases that matter: text over a **gradient** (one ratio per run is a fiction — the string's two ends sit on different colours), over images or canvas, under translucent overlays, and near `backdrop-filter`. That script screenshots the page, decodes the PNG, and samples the surface pixels actually around each run, reporting `inner` (against the dominant measured backdrop) and `worst` (the nearest-luminance surface pixel). A run can pass `inner` and fail `worst`; that gap is the hidden failure, and no computed-style checker can see it.

   **For a single comparable number**, run `node scripts/accessible-score.mjs <file.html ...>`, which consumes the same audit and ranks several pages against each other across five weighted dimensions — legibility 22%, comfort 24%, hierarchy 20%, length 24%, robustness 10% — with a letter grade. Two properties of it matter more than the number:
   - **Gates dominate points.** A page with a WCAG floor violation, halation on the reading surface, or clipped content cannot average its way into the top band with generous padding; it is capped and labelled, however high its other dimensions run. Comfort-ceiling and systemic target failures cap less severely. This is deliberate — a composite that lets legibility be traded against whitespace is measuring the wrong thing.
   - **`--exclude` marks low-dwell chrome and is exempt from the *ceiling* only.** A saturated brand-hue rail may be loud; its text still has to be readable. Passing `--exclude` and having it suppress floor checks too would hide exactly the failures chrome tends to contain.
   - Rank pages against each other with it; do not read "84 vs 88" as a meaningful gap. The weights are calibrated on a handful of human judgements, not a corpus.
2. **Actually look at `render.png`.** Do not skip this and trust the numbers. The script cannot see a fund-code chip whose text spills into the name beside it, a filter row that wrapped and left dead space, a sticky bar sitting over the last row's content, a column that lost its alignment, or a heading that reads as decoration rather than structure. Those are the failures people notice first. Look at the image and name what's wrong with it, in your own words, before declaring the numbers sufficient.
3. **Answer the mode checklist against what you saw**, item by item, pass or fail — not a summary sentence claiming you checked.
4. **Fix, re-render, re-check.** Repeat until clean. After three loops without converging, stop and report honestly which items remain unmet and why, rather than quietly delivering.
5. **Compare numerically against a reference** when one exists: `--baseline reference.json` prints a delta per metric. If the person has already approved an output as "this is what I want", audit that file once, keep its report, and use it as the baseline for everything after — it turns "is this as good as the one I liked?" into a number.

**Mode checklist.**

*Lite* — every diagnosed crowding item addressed within the moves Lite permits; type/spacing visibly opened relative to the input (measure the median font size and block gap against the original, don't eyeball it); no layout region moved, no page added, no navigation changed; nothing dropped.

*Medium* — everything in Lite, plus: each question from the redistribution list has its own projection; the detail unit now carries measurably fewer distinct facts per row than the input did (if the count is unchanged, the data was restyled, not redistributed — see `references/principles.md`); one job per unit; non-scanned values folded to plain text; new shared action surfaces are in predictable fixed positions.

*Ultra* — everything in Medium, plus: output is multiple pages/files or the single-page exception is stated in one sentence; token layer rebuilt as a tonal ramp; real elevation system; every stat/filter/action from the source still present somewhere; brand still recognisable; each page's *name* matches the density of what landed under it; the working-surface light/dark call from step 5 was actually applied and not quietly reverted mid-build. **For a pass over an app rather than a single page, also: the navigation grouping was re-derived from the jobs people are doing rather than inherited from the input, every catch-all bucket ("Settings", "System", "Misc") was emptied on paper and only its genuinely jobless survivors left in, sibling categories are comparable in size, the nav grouping and the permission/role grouping agree with each other, and the route paths say what the pages are** — or each of those was explicitly left alone with a stated reason, not silently.

*Every mode* — the comfort ceilings: no sustained-text pairing above the ceiling, no high-chroma colour on a near-black working surface, no unbroken multi-screen run without a structural signpost, form controls and buttons at least 24px (44px comfortable), nothing clipped, no page-level horizontal overflow. Small *text links* in breadcrumbs, nav and prose are exempt — advisory, not failures, and treating them as breaches hides the real ones.

**Two traps specific to this step.**

*A passing contrast check is not proof of comfort.* WCAG is a floor. If the script reports zero AA violations, that says nothing about the ceiling — read the ceiling and halation counts too, and treat "AA clean, ceiling dirty" as a failure, not a wash.

*If you write or adapt any colour-measuring code, resolve colours by rasterizing.* Browsers hand back `oklch()`, `oklab()`, `lab()`, `lch()`, `color-mix()` and `color()` **exactly as authored** in computed styles — and canvas `fillStyle` echoes them back too, so neither string-parsing nor reading `fillStyle` works. Paint a 1px rect and read the pixel with `getImageData`. A checker that silently fails to parse these reports zero violations on every modern palette, which is worse than no checker at all because it looks like a pass. `scripts/accessible-audit.mjs` handles this; if you hand-roll anything, handle it too.

*Lightness is not contrast, and you cannot read one off the other.* In a perceptual colour space, `L` describes how bright a colour *looks to a human*, not its luminance — and equal `L` at different hues gives different contrast ratios against the same ground. Picking a status colour by eye ("L 0.62 is a solid mid tone") produced one that measured **1.9:1** on white while the code comment next to it claimed 4.5:1. Compute the ratio for each hue at the lightness you chose and solve for the lightness that satisfies the floor; do not assume a value that passes for blue passes for amber. The same trap runs the other way when picking ink: a "darker = safer" ramp in oklch compresses near the top, so the last few steps barely move the ratio.

*A theme override that is in the wrong place is not an error — it is silence.* Frameworks that expose a theme/preset object usually ignore any key that does not resolve to a real slot, and keep rendering the old value. A palette rebuilt with the component overrides nested under the wrong branch (a semantic/global section instead of the per-component colour scheme) looked fully applied in the source and changed nothing on screen. The only proof a theme change took effect is a measurement of the rendered result — a screenshot, or a computed style read of the actual painted pixel — never a diff of the config file.

When the output is not renderable HTML — a React/Vue/Svelte component, a native screen, a design file — render whatever you can (dev server, screenshot of the running app, exported image) and inspect that. If genuinely nothing can be rendered, say so explicitly in the delivery rather than implying the visual check happened.
