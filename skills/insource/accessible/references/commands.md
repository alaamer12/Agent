# Commands — multi-file entry points

Loaded only when the person says `taste` or `snippet`. A normal multi-file request without one of those keywords still gets the standard single-pass treatment.

## Commands — multi-file entry points, distinct from a normal single-file pass

Everything elsewhere in this skill describes applying one mode to one input and delivering one result. Two commands change that shape: they operate when the person has handed over **a whole project or many pages**, not a single file, and each produces something other than a single finished pass. Both are triggered explicitly — `/accessible taste [n] <mode>` and `/accessible snippet <mode>` — and neither is the default; without one of these keywords, a multi-file input still gets the normal single-pass treatment (pick the most relevant file, or ask which one, same as always).


### `/accessible taste [n] <mode>` — preview N genuinely different directions before committing

**When to use it:** the person is about to apply this skill across a whole project or a large batch of pages, and wants to see real options before the actual rollout commits to one visual direction. `n` defaults to **3** when omitted; the person can name any count (`/accessible taste 4 ultra`, `/accessible taste 2 medium`). The mode (`lite`/`medium`/`ultra`) still works exactly as documented elsewhere — `taste` changes how many directions get built and how they're delivered, not what each direction contains.

**Picking the sample file.** If the person named a specific file, use it. If they haven't, pick the single file from the project that most exercises this mode's moves — for Ultra, that means the file with the most distinct question-types in view at once (the redistribution test from the moves below), since a thin settings page won't show three directions differing from each other in any meaningful way. State which file was picked and why, in one line, before building — don't build silently against a guess.

**What makes N directions genuinely different, not N minor variations.** This is the part most likely to be faked under time pressure — three passes that only differ by accent hue are not three tastes. Each direction should differ on at least one of the large judgment calls named elsewhere in this skill: working-surface light/dark direction, chrome position (side/top/bottom/floating), chrome color (dark-neutral/light-neutral/full-brand-hue), type/spacing scale (comfortable/large/enormous), page-split shape, or overall density philosophy.

**How to actually arrive at `n` directions, not just list the axes they could vary on.** Listing the axes is not the same as picking real values on them — that's a generation method, and it has three steps:

1. **For each judgment-call axis, ask what this specific input's own constraints actually rule in or out** — the same derive-from-constraints method used for a prior-pass re-approach (see `examples/rerun-detection.md`, point 3): look at what the input's own content and structure make plausible, not at what's abstractly possible. A dozen long, non-iconic nav labels rules out icon-first chrome as a serious option; a nav with 4–5 short, visually distinct items makes it a live option. A product whose current identity is fundamentally tied to a saturated color (that color *is* the brand, not just an inherited choice) makes "drop the brand hue entirely" a weak direction, while "concentrate it in chrome vs. spread it across accents" are both live. Don't skip this step and jump straight to picking combinations — an axis with no plausible alternative for this input shouldn't be the thing that varies between two of the `n` directions.
2. **From the axes that do have more than one live option, choose `n` combinations that are each internally coherent, not just individually defensible in isolation.** A direction is a *design*, not a checklist of independently-chosen values — "light working surface + top-bar chrome + comfortable scale" needs to hang together as something a real product could plausibly ship, not just be three technically-valid answers stapled together. If two axes' live options interact (e.g. a very dense, airy Ultra-scale pairs awkwardly with a floating/collapsible chrome panel that itself eats screen space), let that interaction rule out combinations rather than presenting all of them as equally coherent.
3. **Push for real spread across the `n` you pick, not `n` points clustered near the safest option.** If step 1 leaves 3+ live options on 2+ axes, don't default to picking the `n` closest to the original input's own choices — that reproduces the under-delivery failure this command exists to avoid (see the prior-pass check above: minimal restructuring of something already reasoned-through). At least one of the `n` directions should represent a genuinely different overall feel from the input's current one, not a refinement of it, provided step 1 didn't rule that out as implausible for this specific product.

Pick `n` combinations arrived at this way — not the n most extreme combinations for shock value (that fails step 2's coherence test as often as it passes it), and not n small nudges off a single baseline (that fails step 3). State each direction's defining choices in one line (a "tag," in the template below) before building it, so the person can tell at a glance what's actually different about each card, not just discover it by clicking through.

**Spread is bounded by the constraints — it does not override them.** Step 3 pushes across the axes step 1 found *open*. The dwell-time rule (see the palette move below) is a constraint on which axes are open at all, not one more axis to vary for the sake of variety. Concretely: for a product whose high-dwell-time working surface is read for long stretches — a data-dense admin/ops console, a form-heavy business tool, an analytics table — "dark working surface" is usually **not** a live option, and building it anyway to reach a count of n manufactures a direction this skill would reject on a normal single-file pass. Drop it and substitute a different *open* axis instead (chrome position, chrome colour, scale, density philosophy, page-split shape — these stay genuinely open even when the working-surface direction is settled). Note that chrome's colour and the working surface's light/dark are independent axes, so a bold or identity-saturated direction is still fully available to you even when the surface must stay light: a full-brand-hue rail over a light working surface is a real, unconstrained, genuinely-different direction.

**Building and delivering.** Build each direction as its own complete, self-contained file (or small file set) at the requested mode, in full — a taste preview is not a lower-fidelity sketch of the real pass, it's the real pass, done n times with different judgment-call answers. Then load `assets/taste-picker-template.html` as the shell: fill in one `.taste-card` per direction (name, one-line tag stating what's different about it, and the built file as the iframe's source), regenerate the grid to have exactly `n` cards, and publish the picker alongside the built direction files. The picker is the thing the person interacts with; the individual direction files are what it loads.

**The "Use this one" button copies a prompt — it does not, and cannot, message the agent directly.** A published page has no reliable channel back into whatever is running this skill: inside claude.ai the person can just reply in chat, but the same picker page is just as likely to be opened from a CLI-based agent (Claude Code, a terminal-launched build, or anywhere else this skill runs headless) where there is no chat to reply in at all. Design for that harder case, not just the chat case: each card's button copies a ready-to-paste prompt to the clipboard rather than trying to fire an event the agent might not be listening for. Concretely, when filling in the template:
- Write each card's hidden `[data-role="copy-src"]` content as one self-contained sentence or two naming that direction's actual judgment-call answers (chrome position and color, working-surface direction, scale, page-split) — it has to make sense pasted into a brand-new agent turn with zero other context attached, since the person may paste it into a different session than the one that built it. A vague "use direction A" with no restated content copies nothing useful.
- Leave `data-context` unset unless it's already known for certain which surface will render this page — the template's own script guesses chat vs. CLI from whether the page is embedded, and that guess is usually right; only hardcode `data-context="chat"` or `data-context="cli"` on `<body>` when the calling context is unambiguous (e.g. this skill is explicitly being invoked from within Claude Code).
- Don't strip the copy behavior out to simplify the page even when building for claude.ai specifically — a person can still use it there (copy the prompt into a follow-up message instead of retyping their choice), and it costs nothing to leave in.

**After the person picks — whether by replying in chat or by pasting the copied prompt into a fresh agent turn.** Continue from their choice — either treat it as the finished result for that one file (if that's all they needed), or, since `taste` exists specifically for whole-project rollouts, treat the picked direction's judgment-call answers as the standing defaults for the rest of the project and proceed file-by-file without re-litigating the same calls each time, unless the person says a specific later page should diverge. If the pasted prompt arrives with no other context (a fresh CLI session), treat its restated judgment-call answers as sufficient to proceed without asking the person to re-explain what they already chose on the picker page.


### `/accessible snippet <mode>` — prove the direction on one file before touching the rest

**When to use it:** the person has many files (a whole project) and wants to validate a redesign's *feel* on one representative file before committing to rolling it out everywhere — a lower-overhead alternative to `taste` when the person already has a direction in mind and just wants a fast go/no-go loop rather than a side-by-side comparison.

**Picking the sample file.** Same rule as `taste`: use a named file if given one, otherwise pick and state the one that best represents the project's typical complexity — not the simplest file (which won't reveal problems) and not an outlier (which won't represent the rest).

**Mockup-data, no-source-modification rule — this is what makes `snippet` different from a normal single-file pass.** The first round of `snippet` output is always a standalone rendering — real layout, real styling, real structure, built at the requested mode — but populated with representative **mockup data**, and it is never a modification of the actual source file. This holds regardless of source format:
- If the input file is already plain HTML, the snippet is still a *separate* output file, not an edit made in place to the original — the person is looking at a proof, not a live change, until they say otherwise.
- If the input is written in anything else — any component framework, any templating language, any server-rendered format, whatever the actual source happens to be — the snippet extracts and rebuilds that file's *visual shape* as a standalone HTML mockup. It does not edit the source file itself, in its own language, and it does not attempt to preserve or replicate that source's live data-binding, props, state logic, directives, or server-side logic — none of that transfers to a static HTML proof, regardless of which language or framework it was written in. The output is disposable proof-of-concept markup, not a drop-in replacement for the source file. Say this plainly when delivering a snippet from a non-HTML source — name the source's actual format in that sentence, not a generic placeholder — so the person doesn't mistake the mockup for a ready-to-merge component.

**The like/dislike loop.** After delivering one snippet, stop and ask whether it lands, rather than continuing on to the next file unprompted:
- **If liked** — that direction's judgment-call answers (same set named under `taste` above) become the standing default, and the person can then say to proceed to the next file, or to proceed through the rest of the project. When actually rolling out to the remaining files, that later work *does* modify the real source files in the normal way this skill always has — the mockup-data/no-modification rule is specific to the first proving round, not to the whole command.
- **If disliked** — ask what's off (or take a specific redirect if they already gave one) and rebuild the same sample file's snippet with the new direction, still as mockup data, still not touching source — don't move on to another file until the current one lands or the person says to stop iterating and move on anyway.

`taste` and `snippet` solve the same underlying problem (don't commit a whole project to one direction sight-unseen) from two different angles — `taste` shows several options at once for a side-by-side choice, `snippet` iterates on one option at a time for a faster yes/no loop. Use whichever the person's request matches; if they ask for one by name, that's what they get, without substituting the other because it seems more efficient.
