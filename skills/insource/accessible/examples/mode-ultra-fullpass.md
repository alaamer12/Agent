# Ultra mode: a full pass, assembled

Same starting input as the other two mode files. This one matters most to get right, because Ultra is where two specific mistakes are easiest to make without noticing: quietly staying single-page, and quietly keeping a dark theme dark just because that's what the input already was. Both are documented below as things to actively check for, not just avoid by instinct.

## What Ultra adds on top of Medium

1. **Name the big judgment calls before building anything.** For this kind of input, the calls with the largest effect on the outcome are typically: does the working surface stay dark or break toward light (or some other direction); where does chrome live (side rail, top bar, bottom bar, floating panel — not defaulted to a sidebar); what color is chrome (dark-neutral, light-neutral, or the brand's full saturated hue as its base color, not just an accent on neutral); and does this become one page or more than one. Form a real recommendation for each from what the input itself signals, state it, and proceed with it as the default — see the reasoning below for how to actually judge these, not just default to whichever answer changes the least.

2. **The page-count call.** Take the question list from the redistribution move (same list Medium produces) and count how many distinct questions this input is being asked to answer. If it's genuinely more than roughly two or three (health, trend, comparison, composition, plus row-level detail, is a common real count for a data-dense screen), that's a strong signal to extract the aggregate questions onto their own page — a dashboard/overview page — separate from a page that keeps the row-level detail. **The default at Ultra is to make this split** unless the content is simple enough that one page was never really straining to answer more than one or two questions in the first place (a short form, a single focused tool). Explicitly check, after building: did this end up as one long page with new sections and a new palette? If so, stop — that's a Medium result, and the actual Ultra-defining move (the page split) hasn't happened yet.

3. **The light/dark call, reasoned from what the input actually is.** Ask what this product fundamentally is, using evidence from the input itself: a dark theme applied because the product is inherently a dark-context tool (something like a video/media viewer, a creative tool meant for low-light use) is real signal that dark should probably stay, just softened and better-ramped. A dark theme on a data-dense admin/ops console, a business dashboard, a form-heavy tool — where the darkness doesn't serve the product's actual function, it's just whatever the original build happened to use — is real signal that the working surface (not necessarily the chrome) should break toward a light, low-fatigue treatment instead. **Do not resolve this by defaulting to "keep it dark, just nicer"** without having actually made this judgment — that specific outcome is the one most likely to be a missed call, because it looks like a decision got made (colors did change) while actually avoiding the harder, more consequential decision (which direction the working surface should go). State the reasoning in one sentence either way before building.

3b. **The chrome position and chrome color calls, made independently of the light/dark call above.** These aren't the same decision wearing a different hat — a product can have light-neutral chrome, dark-neutral chrome, or chrome painted in the brand's full saturated hue as its base color (not just an accent stripe on a neutral background), in any combination with either working-surface direction. And chrome doesn't default to a side rail: a top bar, a bottom bar, or a floating/collapsible panel are equally real answers, chosen from this product's actual navigation depth and item count rather than habit. State both calls in a sentence each, same as the light/dark call — three short, explicit judgment statements, not one.

4. **Once the calls are made, build the full re-theme.** A genuine tonal ramp (not a single color swap) gets built for whichever direction was chosen for the working surface, status colors get proper ink/soft-background pairs, and the brand's identity color gets concentrated in whichever chrome region and color direction was chosen (a side rail, a top bar, or otherwise; brand-hue, dark-neutral, or light-neutral) as a deliberate, dominant treatment there — this part of Ultra's reasoning holds regardless of which directions were chosen for the working surface and for chrome.

5. **A full elevation/depth system gets designed**, not nudged — shadows and corner radii reconsidered everywhere at once, reinforced by the new tonal ramp.

6. **Everything Medium already does** (redistribution, one-job-per-unit, pill-vs-text folding, warnings pulled into their own zone) still applies, but now split across however many pages the page-count call determined — typically the redistributed aggregate views live on the new overview-style page, while the restructured, lightened detail rows live on the page that keeps the original row-level list.

## How to tell if an "Ultra" result actually stayed Ultra

Checks matching the judgment calls above, because all are easy to silently fail without any single symptom making it obvious in isolation:

- **Page count**: is the output more than one file/page? If it's one file with a new palette and reorganized sections, that's Medium wearing Ultra's coat of paint — go back and make the split, or state explicitly (one sentence) why this particular input was simple enough to justify staying single-page.
- **Working-surface direction**: did the light/dark call actually get made, or did the working surface just end up dark-but-softer by default? If a genuinely dark-context product justification wasn't actually reasoned through and stated, "still dark" is probably the safe-looking non-decision, not the considered one.
- **Chrome position**: did the design actually consider a top bar, bottom bar, or floating panel, or did it land on a side rail by reflex? If the input already had a side rail and the output kept one without ever stating why that position still fits, that's an inherited default, not a made call.
- **Chrome color**: is chrome dark-neutral by default, or was a light-neutral or full-brand-hue treatment genuinely considered and ruled out (or in) for a stated reason? "Dark sidebar with a colored accent" showing up again despite never being required by the brand is the same non-decision pattern as the working-surface check above, just in the chrome region instead.

A result that passes all four checks — genuinely multi-page where the input warranted it, with an actually-reasoned working-surface direction, and with chrome's position and color both chosen rather than inherited — is what a complete Ultra pass looks like.
