# Environment, artifacts, and the report

> **Illustrative, not exhaustive.** Engines, runtimes, OS tools and flag names in this file are examples
to reason from. The measurement logic is stack-neutral, and an unlisted or hybrid option is a valid answer.

A timing without conditions is an anecdote. The report has to let a reader on a different machine decide how
much of it transfers.

## Capture the environment (before the run, not after)

| Item | Why it changes numbers |
|---|---|
| OS + build, kernel/allocator version | syscalls, page behaviour, scheduler |
| CPU model, physical vs logical cores, governor, base/max frequency | turbo and governor drift is the biggest single noise source |
| RAM size, swap enabled, NUMA layout | allocation cost, page faults, remote-node penalties |
| Disk type, filesystem, mount options | anything touching persistence (SQLite journal, mmap) |
| Power plan / battery state | a laptop on battery can differ 2–4× and will throttle as it warms |
| Background load at start and end (load average, AV/indexer running) | "why is run 40 slow" is usually a Windows Search index |
| Container/VM, CPU quota, steal time | a cgroup limit or a busy host makes pinning decorative |
| Which isolated environment held the deps | tells a reader whether the numbers need the user's global packages at all — and lets them rebuild the sandbox |
| Runtime + library versions, build flags | `-O2` vs `-O3`, `--release`, GC mode, extension versions |
| What ultra controlled, and what it could not | so a reader knows which question the numbers answer |

```bash
python scripts/bench_stats.py --environment            # prints a filled-in snapshot block, incl. active venv
# and record each candidate's own version from inside the harness:
#   [python] python -c "import sqlite3; print(sqlite3.sqlite_version)"
#   [Node]   node -p process.versions    [Go] go version    [.NET] dotnet --version
#   [Rust/C] the compiled binary's --version, plus the exact build flags used
```

## The isolation record

Two lines the report owes, because "did this run touch my machine?" is the first thing a reader wants to know:

```text
env      : [python -m venv .venv-bench] (temp prefix / container / project's existing env — say which)
         : deps installed there, versions pinned by <lockfile>; project manifests: git diff empty
restore  : machine-wide settings changed → restored, read-back: <governor/power plan/affinity values>
         : scratch artifacts removed → <list>, kept → <list under bench/.../>
```

Capture the "before" values at setup time, not from memory at the end. If the run crashed, that record is the
only way to know whether the machine is still in benchmark configuration.

## Where the artifacts live

```text
bench/2026-10-29-sqlite-search/
├── REPORT.md              the numbers, conditions, verdict, limits
├── environment.txt        the snapshot above
├── samples.csv            candidate,iteration,value — every sample, not aggregates
├── harness/               the runnable scripts, with the workload generator and seed
└── notes.md               decisions made mid-run (a candidate changed, an outlier explained)
```

Rules:
- **The harness is reproducible or it did not happen** — fixed seed, data generated by a script in `harness/`, no
  manual steps that only live in someone's memory.
- Keep the raw samples. Aggregates cannot be re-checked, and the shape of the distribution is usually where the
  story is.
- **Nothing the benchmark needed outlives it.** The isolated env is either kept inside the `bench/` folder
  (documented, gitignored) or deleted; the project's manifests and the user's global package dirs are unchanged.
  State which in the isolation record, and add the env dir to the project's ignore rather than committing wheels
  and `node_modules`.
- A harness that outlives the question belongs in the project's regular place for such things (`bench/`,
  `benchmarks/`, a `-bench` target). If the session produced something a future agent would rerun, that is a
  [`bequeath`](../../bequeath/SKILL.md) candidate — `bench/` is a project asset, not a `bequest/` one; bequeath
  the *how we measured this* procedure instead.

## The report

```markdown
# <question, as a decision>: <A> vs <B>

**Verdict.** <one or two lines: which wins on which dimension, by how much, and whether the gap clears the
noise floor. If it does not: "no measurable difference at this resolution" — that is a result.>

**Dimensions measured.** <name · metric · unit · what it answers>  · **Not measured.** <the honest tail>

| Candidate | Median | p95 | MAD | CV | vs baseline | Verdict |
|---|---|---|---|---|---|---|
| indexed | 1.9 ms | 2.4 ms | 0.2 | 9 % | 1.00× | — |
| scan | 214 ms | 261 ms | 11 | 6 % | 112× | 95 % CI [98×, 126×] — clears the floor |

**Correctness gate.** <same rows/values within <stated tolerance>, on N real inputs; any divergence listed as the
headline finding>

**Conditions.** mode <normal|ultra> · language/versions · isolated env <venv/temp prefix/container; manifests
unchanged> · hardware/OS snapshot (or a file reference) · workload (<size>, <distribution>, seed) · iterations
<n> (warmup <w>) · interleaved A/B · controls applied and restored · controls not possible · scratch artifacts
removed · date/time · <noise floor from A vs A′>

**What this does not tell us.** <untested sizes, other platforms, cold vs warm, tail behaviour under load,
memory omitted, "we did not test the 100× case">

**Reproduce.** <exact commands, and the expected runtime>
```

Phrasing that keeps a report honest:
- *"B was 1.3× slower at this size on this machine"* — not "B is slower".
- *"the difference is inside the noise floor (4 %), so this run cannot rank them"* — not "B is basically equal".
- *"we measured the wrapper, not the engine"* — when the fixed overhead rivals the work
  ([`../SKILL.md`](../SKILL.md), step 3).

## When the result contradicts expectation

If the "obviously faster" candidate loses, that is the finding — report it loudly and check three things before
doubting the claim: (1) is the harness deleting work or measuring itself, (2) did one candidate get a warm cache
or a lucky core, (3) is the workload actually the real one. Fixing any of those changes the number, so verify
before publishing a surprise. A contradiction between a run and a belief is usually a broken harness; a
contradiction after the harness is checked is new information.
