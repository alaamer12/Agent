# Shared Workspace Protocol

## Directory layout

Pick a workspace root before launching anyone:

```
<workspace-root>/            # CWD, or a fresh temp dir for isolated experiments
├── conversation.txt         # (or conversation_<n>.txt for multiple parallel debates)
├── conversation.txt.lock    # lock file, only if using scripts/collab_log.py
└── artifacts/               # optional: per-agent files, evidence dumps, test outputs
```

Use one log file per independent discussion. If you run several unrelated debates in
parallel, give each its own file (`conversation2.txt`, `conversation3.txt`, ...) so
sequence numbers and locks don't collide.

Avoid letting agents write to arbitrary files in the workspace root without a clear
namespace — if an agent needs to produce an artifact (e.g. a proposed patch, a benchmark
result), have it write to `artifacts/<agent-name>/...` so agents can't clobber each
other's output.

## Message format

Every committed message should carry enough metadata to reconstruct order and timing
even under concurrent writes:

```
sequence: <monotonically increasing integer>
sent_at: <ISO-8601 timestamp with sub-second precision, generated by whoever commits the
message, not trusted from the agent>
sender: <persona/agent identifier, e.g. SCRUM_MASTER, SECURITY_REVIEWER>
content:
<message body>
---
```

Rules:

- **New messages go at the top** of the file (most recent first). This keeps "what's the
  latest state of the discussion" a cheap read of the first block, which matters when
  many agents poll the file frequently.
- **Sequence number is authoritative**, not the timestamp. If two messages land in the
  same millisecond, the sequence number — assigned at the moment of commit — decides the
  real order.
- **Never edit or delete a committed message.** If an agent wants to retract or correct
  something, it posts a new message that says so; the log is append-only history.
- Only one process (or a locked helper like `scripts/collab_log.py`) should ever
  actually write to the log file. Never let two independent writers do an unsynchronized
  read-modify-write on the same file — you will lose messages.

## Duplex vs full-duplex

- **Duplex**: an agent's normal loop is *wait until someone addresses me → react →
  respond → wait again*. Good for tightly turn-based collaboration (e.g. two roles
  ping-ponging one point at a time).
- **Full-duplex**: an agent posts into the shared space whenever it has something to
  contribute, without waiting to be addressed, and other agents may react to any message
  regardless of who wrote it or when. Good for open debates with 3+ participants where
  strict turn-taking would be artificial.

In both modes, an agent's loop is fundamentally:

```
read log → find anything new since my last read → decide whether/how to react →
(optionally) post a message → wait briefly → repeat
```

Tell each subagent explicitly to keep looping (read/react/post/wait) rather than exiting
after a single message, if the communication mode requires ongoing exchange. Subagents
that finish after one turn will silently kill a discussion that was supposed to run
until a time limit or termination condition — make the persistence requirement explicit
and impossible to miss in the prompt.

## Concurrent writers (full-duplex safety)

If multiple agents can write near-simultaneously, the workspace mechanism must
serialize commits: acquire a lock, read current state, assign the next sequence number,
build the new message, write atomically (temp file + rename, not an in-place edit),
release the lock. `scripts/collab_log.py` implements exactly this if your runtime lets
subagents run shell commands against a shared filesystem.

If your runtime cannot give subagents shared filesystem/shell access (e.g. subagents
only return text to you), you are the serialization point: collect messages as they
arrive, append them to the log yourself in the order you received them, and hand the
updated log to whichever subagent needs to see it next.

## Exact commands to put in a subagent's prompt

The communication mechanism is only useful if every subagent prompt tells the agent
*exactly* which commands to run, not just "use the shared log". When delegating with
`scripts/collab_log.py` (or an equivalent locked helper), give each subagent the literal
command lines, e.g.:

```
To read the current discussion:
    python <path-to-skill>/scripts/collab_log.py --file conversation.txt read

To post a message:
    python <path-to-skill>/scripts/collab_log.py --file conversation.txt send --sender SCRUM_MASTER --content "<your message>"
```

Also make the persistence loop explicit and literal, e.g.:

```
1. Read the log.
2. If the newest message is from someone else, react to it and send your response.
3. If the newest message is already yours, wait a few seconds (e.g. `Start-Sleep -Seconds 4`
   or `sleep 4`) and read again.
4. Repeat until the session ends or you are told to stop — never exit after one message.
```

Copy `scripts/collab_log.py` into the working directory (or reference its absolute path)
before delegating any subagent, and `init` the log file first, so the very first `read`
an agent performs doesn't fail on a missing file.

## Alternative: a single mutable scratch file (no lock, no sequence numbers)

`scripts/collab_log.py` is the recommended default because it guarantees no lost
messages under concurrent writers. But for a **duplex, two-agent, strictly turn-based**
collaboration where only one agent is ever supposed to write at a time, a simpler
pattern is sometimes acceptable: a single mutable file (e.g. `msg.txt`) that always holds
only the latest message, which each agent reads, then overwrites when it's their turn.

Trade-offs versus the append-only locked log:

- Pros: trivial to implement (`open`/`create`/`search_replace` on one file, no script
  needed), fine when strict alternation is enforced by the prompt itself.
- Cons: no history — once overwritten, the previous message is gone, so you cannot
  reconstruct the full discussion afterwards unless something else also appends it to a
  permanent record. No protection against two agents writing at once, so it only works
  in **duplex** mode, never full-duplex. No authoritative sequence number, so ordering
  relies entirely on the agents correctly alternating turns.
- Use this only when: the mode is duplex, there are exactly two participants, losing
  intermediate history is acceptable (e.g. the orchestrator doesn't need a full
  transcript afterward, or a separate append-only log is kept alongside it), and the
  simplicity is worth more than the durability guarantees.

Prefer `scripts/collab_log.py` (or an equivalent append-only, locked, sequence-numbered
log) whenever the final report must reconstruct the full chronological discussion, or
whenever more than two agents / full-duplex communication is involved.
