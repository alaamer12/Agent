# Native drift: when the archive changes what gets compiled

The archive does not just carry source — it decides whether the builder generates
the native project at all. Most "works locally, fails in the cloud" Expo build
failures are this.

## Continuous native generation (CNG / prebuild)

`expo prebuild` writes `android/` and `ios/` from `app.json`, plugins, and the
installed package versions. If the project does not commit those directories, the
builder must generate them.

**Detection:** the build log's first line names the directory Gradle or xcodebuild
runs in, e.g. `Running 'gradlew :app:assembleDebug' in /home/expo/workingdir/build/apps/mobile/android`.
That alone does not prove prebuild ran — check the Gradle or CocoaPods version
banner against what a local `expo prebuild` produces:

```
cd <app> && rm -rf android ios && bunx expo prebuild --platform android --no-install
grep distributionUrl android/gradle/wrapper/gradle-wrapper.properties
```

If the builder's version is older than the freshly generated one, the builder used
an uploaded folder instead of generating.

**Symptom:** `Minimum supported Gradle version is X. Current version is Y`, or an
AGP/compileSdk/NDK mismatch, or a Podfile error. The uploaded directory was
generated by an older SDK, and the toolchain versions pinned inside it
(`gradle-wrapper.properties`, `Podfile.lock`, `.xcworkspace`) now disagree with the
dependency versions the builder just installed.

**Fix:** exclude the generated directories from the archive so prebuild runs.
Remember the rule from `easignore-semantics.md`: if `.easignore` exists, a nested
`.gitignore` inside the app package has no effect on the archive — the exclusion
must be in the file the archiver actually reads. Then delete the stale local
directory, or regenerate it, so local and cloud stop disagreeing.

**Never** "fix" this by editing the uploaded folder's wrapper version. That treats
the symptom and re-introduces the drift on the next SDK upgrade.

## Memory: `Gradle build daemon disappeared unexpectedly`

This message means the daemon process was killed from outside — the JVM did not
report an out-of-memory error, the OS did. Read where the log stopped:

- Stops during `buildCMakeDebug[...]` / `configureCMakeDebug[<abi>]` / many
  `:module:*` tasks in parallel → native compile fan-out.
- Stops during a bundling task → JavaScript bundle memory.

**The lever is fan-out, not heap.** Each additional ABI recompiles the whole native
graph (Reanimated, Gesture Handler, MMKV, `expo-modules-core`, autolinked modules),
so peak resident memory scales with the ABI count while the Gradle and Kotlin
daemons sit on top of it. Raising `-Xmx` on a memory-capped builder makes the kill
more likely, not less.

Reduce the set of ABIs for the profile that needs it. Prefer a per-profile
environment override so release builds keep full device coverage:

```json
"development": {
  "env": { "ORG_GRADLE_PROJECT_reactNativeArchitectures": "arm64-v8a,x86_64" }
}
```

Any Gradle property can be injected this way: the name after `ORG_GRADLE_PROJECT_`
is the property name verbatim (dots allowed), and it takes precedence over
`gradle.properties`. That matters under CNG, where the generated
`android/gradle.properties` is rewritten on every prebuild and cannot hold an edit.
The equivalent file-based route is the `expo-build-properties` plugin
(`android.buildArchs`), which applies to **every** profile — a release-size change
dressed as a build-speed fix, so choose deliberately.

For iOS the same reasoning applies in reverse: cut work rather than grow the heap —
fewer build configurations, fewer simulators, and avoid shipping a committed `Pods/`
or `Podfile.lock` that disagrees with the installed package versions.

## `Cannot find native module 'X'` in a custom dev client

Native modules are compiled into the client at build time. The JS/native boundary
determines which change requires which action:

| Change | Needs a new client? |
|---|---|
| Component, hook, route, style logic | no |
| Config plugin option that alters generated files | yes |
| Adding/removing an Expo or native module package | **yes** |
| Bumping a native module's major | **yes** |

So a crash naming a module the JS asks for is fixed by declaring the package and
rebuilding — not by clearing Metro's cache. Confirm the package is a real
dependency and that it ships an autolinkable descriptor:

```
cat node_modules/<pkg>/expo-module.config.json   # android/apple module entries
```

If the descriptor exists and the package is declared, the next build will contain
it. Tell the user to install the **new** client; the old binary keeps failing
identically.

## Version skew: an undeclared package resolving from a stale store copy

Symptom: the stack trace shows a package version that matches no manifest — e.g.
an SDK-57 copy of a library inside an SDK-58 app, with paths under
`node_modules/.bun/<pkg>@<ver>+<hash>/` (bun) or `.pnpm/` (pnpm).

Cause: the package was a dependency before an upgrade, is still physically present
in the store's hoisted layer, and something resolves it from there. Often the app's
own code imports it too, so it is an **undeclared dependency that happens to work**.

Trace who links what before deleting:

```
find node_modules -maxdepth 7 -path "*/<pkg>" -printf "%p -> %l\n"
node -e "console.log(require('./<app>/node_modules/<pkg>/package.json').version)"
```

Fix in this order, because the wrong order breaks the app:

1. Declare the correct version (`bunx expo install <pkg>` picks the SDK-matching
   one; a bare `add` may grab `latest`).
2. Reinstall cleanly so the stale store copies stop being resolvable.
3. Rebuild the client — the newly declared native module has to be compiled in.

Purging stale copies first would break the import that depends on them.
