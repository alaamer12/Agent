## 1. SVG correctness and optimization

### 1.1 viewBox, width/height, preserveAspectRatio — why a logo's edges get cut

**viewBox semantics.** "The `viewBox` attribute defines the position and dimension, in user space, of an SVG viewport… The resulting viewBox is a rectangle in user space mapped to the bounds of the viewport of an SVG element (not the browser viewport). When an SVG contains a viewBox attribute (often in combination with a preserveAspectRatio attribute), a transform stretches or resizes the SVG viewport to fit a particular container element." Values `width` or `height` `<= 0` "disable rendering of the element".
[VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Attribute/viewBox (spec pointer: SVG 2 `coords.html#ViewBoxAttribute` https://w3c.github.io/svgwg/svg2-draft/coords.html#ViewBoxAttribute)

**preserveAspectRatio semantics.** [VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Attribute/preserveAspectRatio
- "if `viewBox` isn't set, the `preserveAspectRatio` attribute has no effect on SVG's scaling" (except `<image>`). So a crop/resize bug where PAR "does nothing" means the viewBox is missing.
- Default is `xMidYMid meet`; `meet` = aspect preserved, "the entire viewBox is visible within the viewport", and consequently "the area into which the viewBox will draw will be smaller than the viewport" (letterboxing, not cutting).
- `slice` = aspect preserved, "the entire viewport is covered by the viewBox", so "some of the viewBox will extend beyond the bounds of the viewport" — **this is the literal "edges cut off" setting.**
- `none` = "Does not force uniform scaling… non-uniformly… such that the element's bounding box exactly matches the viewport rectangle" (stretch/distort; the `<meetOrSlice>` part is ignored). Align values are the 9 `x{Min|Mid|Max}Y{Min|Mid|Max}` combos plus `none`.

**Clipping is on by default.** [VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Attribute/overflow — "Although the initial value for overflow is `auto`, it is overwritten in the User Agent style sheet for the `<svg>` element when it is not the root element of a stand-alone document, the `<pattern>` element, and the `<marker>` element to be hidden by default." And "If the `overflow` property has the value `hidden` or `scroll`, a clip of the exact size of the SVG viewport is applied." Consequence: anything (a stroke, a control point overshoot, a badge) drawn outside the viewBox rectangle disappears; `overflow: visible` on the root is the escape hatch for inline SVG.

**SVG as a CSS background / `<img>` sizing algorithm.** [VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Backgrounds_and_borders/Scaling_SVG_backgrounds
- Four rules: (1) a fixed `background-size` dimension wins; (2) else preserve the image's **intrinsic ratio**; (3) else a specified size wins; (4) else "the image is rendered at the same size as the background area".
- "The browser renders `<svg>` images as `300px` wide and `150px` tall by default" when nothing is declared.
- viewBox supplies the **intrinsic ratio**; width/height supply the **intrinsic size**; "An SVG image with fixed dimensions will be treated just like a raster image of the same size."
- "If you are trying to stretch your SVG to a different aspect ratio with CSS… make sure your SVG includes `preserveAspectRatio="none"`."
- Practical reading of the doctrine symptom: an SVG that ships **width/height but no viewBox** (the classic `removeViewBox` output) is a fixed-size raster-like image inside `<img>`/background — it will not fill the box, will letterbox or overflow, and will clip when the container is smaller. [REASONED + the SVGO warning below]

**Diagnosis order for "logo edges cut off"** [REASONED, each step grounded above]:
1. Missing `viewBox` (check for baked `width`/`height` only) → no scaling at all, clip in small containers.
2. viewBox tighter than the artwork (export selected layer, not the frame) + default `overflow:hidden` → the cut part is genuinely outside the viewport.
3. `preserveAspectRatio="… slice"` or CSS `object-fit: cover` on the media element → intentional cropping.
4. Stroke drawn exactly on the canvas edge: a centered stroke loses half its width outside the box → the frame must be padded (Lucide mandates ≥1px clearance, §2).
5. Non-integer scale factor (viewBox 0 0 1024 1024 rendered at 33px) → seams/soft edges rather than cuts (§1.4).

### 1.2 SVGO: which options bite

**removeViewBox.** [VERIFIED-fetched] https://svgo.dev/docs/plugins/removeViewBox/ — "Removes the viewBox attribute where it matches the documents width and height." Then, verbatim danger callout: **"This plugin prevents SVGs from scaling, so they will not fill their parent container, or may clip if the container is too small."** (context link svg/svgo#1128).

**Is it a default?** No — in SVGO v4 the `preset-default` list does **not** contain `removeViewBox` (nor `removeDimensions`, `removeTitle`, `removeScripts`, `removeStyleElement`), but **does** contain `convertShapeToPath`, `convertPathData`, `cleanupNumericValues`, `mergePaths`, `collapseGroups`, `cleanupIds`, `removeHiddenElems`, `removeUselessStrokeAndFill`, `removeDesc`, `removeEditorsNSData`, `removeUnknownsAndDefaults`, `convertColors`, `convertTransform`, `sortAttrs`, `inlineStyles`, `minifyStyles`. [VERIFIED-fetched] https://svgo.dev/docs/preset-default/ — also note the caveat "If you aren't using SVGO directly, like through SVGR, the default plugins may differ from the default preset."

**Dangerous-by-association defaults inside preset-default:**
- `convertPathData` (default, since v0.0.7): converts relative↔absolute "whichever is shortest", converts curves to lines/arcs "that behave like" each other, removes redundant commands, trims leading zeros, and **"Round numeric values using conventional rounding rules"**, with documented `floatPrecision: 3` and `transformPrecision: 5` in its parameter example. Baking transforms into path data (`applyTransforms`, `applyTransformsStroked`) is what turns a crisp 24-grid icon into fractional coordinates. [VERIFIED-fetched] https://svgo.dev/docs/plugins/convertPathData/
- `cleanupNumericValues` (default): "Rounds numeric values, removes the unit when it's `px` as this is the default, and removes redundant spaces", parameters `floatPrecision: 3`, `leadingZero: true`, `defaultPx: true`, `convertToPx: true` (converts `cm`/`in` to `px`). [VERIFIED-fetched] https://svgo.dev/docs/plugins/cleanupNumericValues/
- `convertShapeToPath` (default): "Convert basic shapes to `<path>` elements", with `convertArcs: false` and `floatPrecision: null` as documented defaults. Turning `<circle>`/`<rect>` into `d=` data costs editability, round-tripping, and (for `rect` with rx) sometimes visual equality; `convertArcs` off keeps circles as circles. [VERIFIED-fetched] https://svgo.dev/docs/plugins/convertShapeToPath/
- `removeDesc` (default) drops `<desc>`; `removeTitle` exists but is **off** by default — so an optimized SVG keeps its accessible name but may lose its long description. Flag this in doctrine: run SVGO on artwork, then re-assert `<title>`/`<desc>`/`role` in a second, a11y-aware pass or keep the authored source as the a11y-of-record. [VERIFIED-fetched list] https://svgo.dev/docs/preset-default/ + [REASONED consequence]
- `cleanupIds` + `mergePaths` + `reusePaths` interact badly with `currentColor`/per-part CSS hooks and with `<style>` class hooks; if a component styles `path:nth-child(n)` or classes, disabling these plugins is the safe move. [REASONED from the plugin list and §1.5]
- Wrapper drift: SVGR pre-v6 applied its own SVGO config that removed viewBox; "Configurations are not merged any more, it means you have to remove viewBox by yourself if you use a custom SVGO config". [VERIFIED-fetched] https://react-svgr.com/docs/migrate/ (corroborates the "SVGO used to eat viewBox / wrappers differ from SVGO defaults" claim; the same page appears as [SEARCH-asserted] in query results.)

**Doctrine position:** keep `removeViewBox` off (it is off by default in v4 — the real risk is stale configs, `imagemin-svgo` presets, and older SVGR pipelines that re-enable it; that drift is why it must be pinned in the repo config, not trusted to defaults). [REASONED]

### 1.3 Rounding-induced sub-pixel gaps (the 0.5px hairline problem)

- The mechanism: fractional coordinates after transform-baking or precision collapse (§1.2) plus a non-integer scale factor (viewBox→CSS px) means adjacent shapes sample onto different device-pixel grids, and anti-aliasing leaves a lighter seam between them. [REASONED]
- The authoritative mitigation is to design on an integer grid and keep gaps ≥ 2px: Lucide's spec mandates "Coordinates **should** align to the pixel grid where possible", "Centers of arcs and other geometric elements **should** align to the pixel grid where possible", "Distinct elements **must** have at least 2 pixels of visual separation", "Gaps between distinct elements **must not** be smaller than 2 pixels", and allows off-grid geometry "when required for visual balance… Pixel alignment **should not** take precedence over the visual quality of the icon". [VERIFIED-fetched] https://lucide.dev/contribute/icons/specification (and its `.md` endpoint, which the site explicitly offers for machines: "Are you an LLM? You can read better optimized documentation at /contribute/icons/specification.md")
- A 2px gap on a 24-unit canvas is exactly 1px at 12px render and 0.67px at 8px: the "hairline gap" appears the moment the design rule is thinner than that (1px strokes/gaps on a 24 grid at small sizes). [REASONED]
- `shape-rendering` / `image-rendering` exist as knobs (`crispEdges` etc.) but forcing them on vector art trades seams for jaggies; treat as a last resort on non-animated, axis-aligned tiles. [REASONED; attributes exist: https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Attribute/shape-rendering — not fetched in this session]

### 1.4 Stroke vs fill icons; non-scaling-stroke

- `vector-effect="non-scaling-stroke"`: "This value modifies the way an object is stroked… The resulting visual effect of this value is that the stroke width is not dependent on the transformations of the element (including non-uniform scaling and shear transformations) and zoom level." Default `none`. CSS property takes priority over the presentation attribute. The spec's other three values — `non-scaling-size`, `non-rotation`, `fixed-position` — "have no implementations and are considered at-risk". [VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Attribute/vector-effect
- Doctrine: a stroke-based icon set is a *typographic* system — stroke width must scale with the icon, which is the opposite of `non-scaling-stroke`. Use `non-scaling-stroke` for maps/diagrams/data overlays where 1px is a requirement, and never let it silently ride along from a Figma export into an icon set. [REASONED from the definition]
- Fill icons are immune to stroke-scaling drift but lose the "one file, N weights" property of stroke icons; stroke icons are also vulnerable to `convertShapeToPath` + `removeUselessStrokeAndFill` and to `stroke-width` being treated as a presentation attribute with zero specificity (see scripting guide: "Presentation attributes are treated as author-origin declarations with a specificity of zero, inserted at the start of the author style sheet, so any rule in a style sheet overrides them"). [VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/SVG/Guides/Scripting — this is exactly why the Lucide CSS-class pattern (`.lucide-icon { stroke-width: 2 }`) works, and why baked-in attribute stroke-width is the fragile choice.

### 1.5 currentColor and the multi-colour trap

- `color` (SVG) "is used to provide a potential indirect value, `currentColor`, for the `fill`, `stroke`, `stop-color`, `flood-color`, and `lighting-color` attributes", and it is inherited; "Technically, `color` can be applied to any element, but it has no direct effect on SVG elements." [VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Attribute/color
- Consequence (doctrine): one `currentColor` resolves to **one** colour per element subtree. A multi-colour artwork that uses `fill="currentColor"` on two paths in the same subtree becomes monochrome the moment an ancestor's `color` changes (hover, dark mode, active). Real multi-colour needs explicit `fill="#…"`, or separate CSS custom properties (`fill: var(--icon-primary)` / `var(--icon-secondary)`) set from the component, or `stroke` for line parts + `fill` for badge parts with different tokens. [REASONED from the verified inheritance rules]
- The sprite/CSS-var pattern in the wild is visible in real production CSS: rive.app's own stylesheet ships `unicode-range`-split Google Fonts `@font-face` blocks with `font-display: swap` — i.e. the same `fill`/`stroke` cascade applies to inline icons and text alike. [SEARCH-asserted, incidental]

### 1.6 SVG sanitizer security (untrusted SVG)

**Where scripts run — official.** [VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/SVG/Guides/Scripting
- "Inline SVG in an HTML document. The SVG elements are nodes in the HTML document, so the page's own scripts can query and modify them directly."
- "A standalone SVG document. An SVG file can carry its own scripts in the SVG `<script>` element. Those scripts run when the file is loaded as a document: opened directly, or embedded with `<object>`, `<iframe>`, or `<embed>`."
- "SVG used as an image. When an SVG is referenced by `<img>`, the SVG `<image>` element, or a CSS property such as `background-image`, it is rendered in a secure, non-interactive mode: its scripts never run and its links can't be activated."

**What else is disabled in image mode.** [VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/SVG/Guides/SVG_as_an_image — "For security purposes, some browsers place restrictions on SVG content when it's being used as an image": JavaScript disabled; "External resources (e.g., images, stylesheets) cannot be loaded, though they can be used if inlined through `data:` URLs"; `:visited`-link styles aren't rendered; platform-native widget styling disabled. And crucially: "the above restrictions are specific to image contexts; they don't apply when SVG content is viewed directly, or when it's embedded as a document via the `<iframe>`, `<object>`, or `<embed>` elements."
→ **Doctrine line: `<img>`/`background-image` = sandboxed; inline, `<object>`, `<iframe>`, `<embed>`, or a same-origin direct navigation = script-bearing.** Serving untrusted SVG from your own origin in any non-image mode is the classic stored-XSS shape. [VERIFIED-fetched framing + REASONED conclusion] Corroboration: a real stored-XSS advisory for exactly this — "The application does not sanitize uploaded SVG files" (SiYuan GHSA-pcjq-j3mq-jv5j) [SEARCH-asserted] https://github.com/siyuan-note/siyuan/security/advisories/GHSA-pcjq-j3mq-jv5j, and the general attack taxonomy (embedded JS via event handlers or script tags, inline rendering context) at https://pentesterlab.com/glossary/svg-xss [SEARCH-asserted].

**The standardized answer: HTML Sanitizer API.** [VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/API/HTML_Sanitizer_API
- Safe methods `Element.setHTML()`, `ShadowRoot.setHTML()`, `Document.parseHTML()`; unsafe counterparts `setHTMLUnsafe()` etc. "The safe methods should be used instead of `Element.innerHTML`… for injecting untrusted HTML content."
- "The XSS-safe baseline configuration defines the items that must be removed… `<embed>`, `<frame>`, `<iframe>`, `<object>`, `<script>`, **and `<use>`**" plus "All event handler content attributes, such as `onafterprint`, `onbeforeinput`". → Note the trap: the browser's XSS-safe baseline removes `<use>`, which breaks sprite-based icons; and "If a custom sanitizer is used with a safe method, it is implicitly updated to remove any elements and attributes that are not XSS-safe (note that the passed sanitizer is not modified, and might still allow unsafe entities if used with an unsafe method)." So `setHTMLUnsafe` + allow-`<use>` is the deliberate, auditable choice for inline SVG sprites.
- "In general an 'allow configuration' is safer for both the elements and attributes." Also: third-party libraries "should not be necessary when using the safe HTML sanitization methods as the API is integrated with the browser, and is more aware of the parsing context".

**DOMPurify (the incumbent).** [VERIFIED-fetched] https://raw.githubusercontent.com/cure53/DOMPurify/main/README.md (v3.4.18)
- "DOMPurify is a DOM-only, super-fast, uber-tolerant XSS sanitizer for HTML, MathML and SVG." Default permits all three; `USE_PROFILES: { svg: true, svgFilters: true }` for SVG-only; `NAMESPACE: 'http://www.w3.org/2000/svg'` for a different root namespace; sample: `DOMPurify.sanitize('<svg><g/onload=alert(2)//<p>')` → `<svg><g></g></svg>`.
- Foot-guns stated in the doc: sanitize-then-modify "voids the effects of sanitization"; **closed shadow roots cannot be sanitized** ("One thing DOMPurify cannot sanitize is the content of a closed shadow root… do not parse untrusted markup that way before handing the node to DOMPurify" — i.e. avoid `setHTMLUnsafe()`/`parseHTMLUnsafe()` on untrusted input before sanitizing); server-side needs latest jsdom, "happy-dom … not considered safe"; `sanitize()` is **not re-entrant** (calling it inside a hook silently swaps the config mid-pass).
- Recommended hook for the `<foreignObject>` vector: "If a `beforeSanitizeElements` or `uponSanitizeElement` hook removes the current node from the tree (for example `node.remove()` to drop a `foreignObject`), DOMPurify treats the node as removed". Also: "Before you widen the allow-list… it's worth skimming the tags and attributes to think twice about".
- `<script>` removal also has a first-party SVGO plugin, `removeScripts` — present in the plugin index but **not** in `preset-default`, so "optimize" ≠ "sanitize". [VERIFIED-fetched] https://svgo.dev/docs/plugins/ (index) + https://svgo.dev/docs/preset-default/ → doctrine: sanitizing untrusted SVG is a separate, named step. [REASONED]

### 1.7 Accessible SVG patterns

[VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/SVG/Guides/SVG_in_HTML
- Example root: `<svg viewBox="0 0 100 100" preserveAspectRatio="xMidYMid slice" role="img">` with `<title>A gradient</title>`; "Including `role="img"` ensures assistive technologies handle the SVG as an image."
- "A `<title>` within an SVG provides the accessible, short-text description of the graphic. The title text is not rendered, but browsers may display it as a tooltip when the SVG is hovered. **The `<title>` should be the first element after the `<svg>` opening tag.**"
- "When an SVG is included via an `<img>` element, the `alt` attribute provides alternative text… Inline SVG does not support the `alt` attribute." "If the image conveys more than a short title, include a longer description with the `<desc>` element."
- Label by visible text: `aria-labelledby`; example `<svg viewBox="0 0 100 125" role="img" aria-labelledby="svgTitle svgDescription">` with `<title id="svgTitle">` and `<desc id="svgDescription">`; "If the SVG can be described by visible text, that text can be referenced with `aria-describedby`. **If aria-describedby is used, it will take precedence over `<desc>`.**" And: "we've included both the description and title in our `aria-labelledby` attribute, as it has better assistive technology support than `aria-describedby`."

[VERIFIED-fetched] https://www.w3.org/WAI/tutorials/images/ — "All non-text content… has a text alternative that serves the equivalent purpose" (SC 1.1.1 A); decorative images → `alt=""`; "Readable text is sometimes presented within an image. If the image is not a logo, avoid text in images" (SC 1.4.5 AA / 1.4.9 AAA). "Removing images from websites (so-called 'text-only versions') make them less accessible and functional for these users."

[VERIFIED-fetched] https://lucide.dev/how-to/accessibility.md — icon-specific, and the most operational of the three: "Lucide icons are hidden from screen readers by default with `aria-hidden="true"`"; "Give icon buttons an accessible name. Put the name on the button or in visually hidden text inside the button, not on the icon"; code block showing the wrong (`<House />` bare, `<House aria-label="Home icon" />`) and right (`<button aria-label="Go to home">`, preferred `<button><House /><span class="visually-hidden">Go to home</span></button>`); "Keep the target size at a minimum of 44 by 44 pixels. The icon itself does not need to be 44 by 44 pixels. The interactive wrapper needs to meet the target size."; contrast ≥4.5:1 per SC 1.4.3; "Use different icons for different meanings… Use the same icon for the same meaning."

## 2. Icon systems

### 2.1 Grids: 16 / 20 / 24, and why mixed styles look cheap

- Lucide's normative rules (must/should vocabulary declared): canvas "must use a 24 × 24-pixel canvas", "must be square", "Icon strokes must remain at least 1 pixel from the edge of the canvas"; "Strokes must be 2 pixels wide", "must use round line joins", "Open paths must use round line caps", "Strokes must be centered on their paths"; spacing "must have at least 2 pixels of visual separation"; corners "Elements at least 8 pixels wide or tall should use a 2-pixel corner radius for 90° corners", smaller ones 1px, diagonals "typically approximately 2.41 pixels"; visual weight "should have a visual weight similar to the `circle` and `square` icons"; shared geometry rules for variants. Tie-break: "When two non-required rules conflict, choose visual clarity and consistency with the Lucide design language." [VERIFIED-fetched] https://lucide.dev/contribute/icons/specification
- Material's grid is the 24dp baseline with downloadable grid templates ("Create your own system and product icons with these Adobe Illustrator files including the 24dp icon grid"). [SEARCH-asserted] https://m2.material.io/design/iconography/system-icons.html (page is an Angular app; not parseable via fetch this session — flagged accordingly.)
- Why mixing reads unprofessional, stated as doctrine: the attributes that make a set cohere are exactly the ones Lucide makes mandatory — stroke weight, cap/join style, corner radius, minimum gap, visual weight, optical vs geometric centring, and reused geometry across variants. Two families (e.g. a 2px round-cap stroke set plus a 1.5px butt-cap set plus a filled set) disagree on all seven at once, and the disagreement is visible at 16px. [REASONED from verified spec]
- Practical corollary: pick **one** style axis per context (stroke set for nav/toolbars, filled set for active states via the documented `variant` mechanism — "Variants of an existing icon should preserve the geometry, placement, and orientation of the base icon") rather than borrowing icons per-glyph from multiple libraries. Apple's variant note gives the same rule natively: "tab bars in iOS default to using a fill variant, so choosing a symbol without a fill variant uses the original symbol". [VERIFIED-fetched] https://developer.apple.com/documentation/uikit/configuring-and-displaying-symbol-images-in-your-ui

### 2.2 Sizing strategy: em / `lh` / px / custom properties

- **em/`lh` (typographic sizing)** is right when the icon lives in a text flow or a labelled control: the SF Symbols approach is text-treaty — "Apply a font text style to a symbol image so that it matches text with the same style. Font text styles also cause symbol images to scale to match the current Dynamic Type setting… Align a symbol image with neighboring text by using the image's baseline." That is the platform-grade argument for `1em`-ish sizing. [VERIFIED-fetched] https://developer.apple.com/documentation/uikit/configuring-and-displaying-symbol-images-in-your-ui
- On the web the same idea is available as `width: 1lh; height: 1lh` for list-item icons: the article's stated problem is that `align-items: start` "caused an even bigger alignment issue. The highlighted area is the line height. The text element height has an empty space above and below it that comes from the font itself", and the section is titled "The solution: using the lh unit"; "Using a fixed value for the transform won't work when the icon size, font size, or container width changes." [VERIFIED-fetched] https://ishadeed.com/article/aligning-list-icons/
- **Fixed px** is right for slots with a hard contract (toolbar buttons, table cells, 16/20/24 steps) where optical rhythm matters more than text tracking. Lucide's own sprite CSS holds `width: 24px; height: 24px` in a helper class while keeping `stroke: currentColor; stroke-width: 2`. [VERIFIED-fetched] https://lucide.dev/guide/static/svg-sprite.md
- **CSS custom properties** are the only way to drive *stroke weight* per context without shipping a second file, and Lucide's site literally exposes this as a runtime knob (`--customize-size`, `--customize-strokeWidth` clamped to 0.5–3, plus a `non-scaling-stroke` class toggle) on its icon pages. [VERIFIED-fetched] https://lucide.dev/contribute/icons/specification (page bootstrap script) + [REASONED] "one token set (`--icon-size`, `--icon-stroke`) owned by the design system; components only change the tokens" is the doctrine conclusion.
- Note the specificity fact that makes token-based theming work at all: presentation attributes lose to any stylesheet rule (specificity zero), so `svg { stroke: var(--icon-color) }` will override `stroke="#000"` in the file. [VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/SVG/Guides/Scripting

### 2.3 Icons inside buttons: the baseline traps

- Inline SVG defaults to inline-level participation in the text baseline. `<video>` docs state the same class of problem for replaced elements ("The `<video>` element is a replaced element — its `display` value is `inline` by default"), and the standard remedy is `display: block` + a flex container; for icons that means the button is `display: inline-flex; align-items: center; gap: …`, not `vertical-align: middle` on the SVG. [VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/video + [REASONED]
- Two distinct traps, both evidenced above: (a) *single-line* icon+label centred with `align-items: center` is fine, but (b) the moment the label wraps to two lines, centring drops the icon to the block's middle and it must be pinned to the first text line — hence `align-items: start` + `1lh` icon height (ishadeed) or a baseline/first-line anchor. Apple does (b) natively with baselines: "you should align the views using their baselines… All system symbol images include baseline information, and `UIImage` exposes the baseline value as an offset from the bottom of the image", with `withBaselineOffset(fromBottom:)` for custom assets and `HStack(alignment: .firstTextBaseline)` in SwiftUI. [VERIFIED-fetched] https://developer.apple.com/documentation/uikit/configuring-and-displaying-symbol-images-in-your-ui
- Third trap: `aria-label` on the icon instead of on the button (double announcement / no name on the control) — see the Lucide code block in §1.7. And the touch-target rule lives on the wrapper, not the glyph.
- Fourth trap [REASONED]: a button with `align-items: center` and a font whose line-height is large will visually sit high because the *text box* (line box) is taller than the cap height; the CSS answer is `text-box-trim`/`line-height: 1` on the label or `1lh`-sized icons, the platform answer is SF Symbols' baseline offset.

### 2.4 Sprites (`<symbol>` + `<use>`) at scale, and their styling limits

- Mechanics: "`<use>` takes nodes from within an SVG document, and duplicates them somewhere else. The effect is the same as if the nodes were deeply cloned into a non-exposed DOM… much like cloned `<template>` elements." [VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Element/use
- **The CSS boundary, verbatim:** "Since the cloned nodes are not exposed, care must be taken when using CSS to style a `<use>` element and its cloned descendants. **CSS properties are not guaranteed to be inherited by the cloned DOM unless you explicitly request them using CSS inheritance.**" → so styling works only for *inherited* presentation properties (`color`/`currentColor`, `fill`, `stroke`, `stroke-width`, `visibility`) set on the `<use>` or an ancestor; direct selectors into the clone (`use .path-2 { fill: red }`) are not a thing. [VERIFIED-fetched, same URL]
- **Attribute precedence gotcha:** "Most attributes on `<use>` are ignored if the corresponding attribute is already defined on the element *referenced* by `<use>`… **Only** the attributes `x`, `y`, `width`, `height` and `href` on the `<use>` element will or may have some effect… However, *any other attributes* not set on the referenced element **will** be applied to the `<use>` element." → a sprite whose symbols hard-code `fill="#0F0"` cannot be recoloured from the outside; the sprite must be authored with `fill="currentColor"`/no baked attributes. [VERIFIED-fetched]
- `<use width>/<height>` "have no effect… unless the element referenced has a viewBox — i.e. they only have an effect when `<use>` refers to a `<svg>` or `<symbol>` element." → the symbol, not the use-site, owns the viewBox; symbols must carry their own viewBox for the sizing to work. [VERIFIED-fetched]
- External sprite files: supported as `href="file.svg#id"` and, in modern implementations, without a fragment for the whole document — "For security reasons, browsers may apply the same-origin policy on `<use>` elements and may refuse to load a cross-origin URL in the href attribute. There is currently no defined way to set a cross-origin policy for `<use>` elements." Plus "Loading resources from data URIs via `<use>`… is deprecated for security reasons." [VERIFIED-fetched] → doctrine: sprites are same-origin only; CDN-hosted sprite files are not a supported pattern, and cross-origin `<use>` is a dead end. And the browser XSS-safe sanitizer baseline strips `<use>` (§1.6), so inline-sprite markup must go through an unsafe-but-audited path or ship the sprite in the document shell.
- Scale/ops tradeoff [REASONED, grounded in the above]: one sprite = one HTTP cache object and one DOM cost per use site, but the whole set is fetched even if three icons are used, per-icon CSS theming is limited to inherited properties, `title`/`desc` inside symbols is unreliable for a11y naming, and any build-time tree-shaking is impossible. Per-icon components (inline SVG) give full CSS control, tree-shaking, and a11y at the cost of markup weight — which is why the JS-icon ecosystems (Lucide/Feather/react-icons) default to components and offer the sprite only as an option ("The sprite is used inline: you put it in your page and reference icons with the `<use>` element. You may also need an additional SVG loader to handle node_modules imports"). [VERIFIED-fetched] https://lucide.dev/guide/static/svg-sprite.md

## 3. Web fonts (also media)

### 3.1 @font-face mechanics practitioners must get right

[VERIFIED-fetched] https://web.dev/articles/font-best-practices
- "**A common misconception is that a font is requested when a `@font-face` declaration is encountered. This is false.** By itself, `@font-face` declaration doesn't trigger font download. Rather, a font is downloaded only if it's referenced by styling that is used on the page." (example: "Open Sans would only be downloaded if the page contained an `<h1>` element") → preload hints that reference never-used fonts are pure waste; the audit must start from CSS usage.
- Discovery order is the real lever: "fonts defined with `@font-face`… aren't discovered until the browser downloads and parses those CSS files"; recommended fix is to **inline the font declarations in `<head>`** rather than preload, with the caveats "Even if only some of the CSS is inlined, the browser still must wait for all the CSS to be loaded, before it can discover if fonts are needed" and "Inlining the font files themselves is not recommended."
- `preload` caution: "using `preload` as a font-loading strategy should also be used carefully as it bypasses some of the browser's built-in content negotiation strategies. For example, **`preload` ignores `unicode-range` declarations**, and if used prudently, should only be used to load a single font format."
- Third-party origins: two `preconnect` hints, one plain for the stylesheet and one **`crossorigin`** for the font host — "Unlike stylesheets, font files must be sent over a CORS connection"; canonical Google Fonts pair: `preconnect` to `fonts.googleapis.com` + `preconnect … crossorigin` to `fonts.gstatic.com`; and "`<link>` includes a `preconnect` resource hint, thus likely results in faster stylesheet delivery than `@import`."
- Format: "Of the modern font fonts, WOFF2… is the newest, has the widest browser support, and offers the best compression. Because it uses Brotli, WOFF2 compresses 30% better than WOFF" plus the quoted practitioner verdict: "Use only WOFF2 and forget about everything else… This will simplify your CSS and workflow massively and also prevents any accidental double or incorrect font downloads." (Bram Stein, 2022 Web Almanac) [VERIFIED-fetched, same URL]
- Subsetting: "`unicode-range`… informs the browser which characters a font can be used for. A font file is downloaded if the page contains one or more characters matching the unicode range. `unicode-range` is commonly used to serve different font files depending on the language used by page content." Latin ≈100–1000 glyphs, CJK "may have over 10,000 characters"; Google Fonts ships per-script subsets automatically (the doc pastes a Poppins devanagari/latin-ext/latin triple with `font-display: swap`); "When moving to self-hosting, this is an optimization that can be missed and lead to larger font files locally." Tools: subfont, glyphhanger; Google Fonts `text=` parameter; and the licensing line "**Always check the font licenses to confirm they allow subsetting and self-hosting.**"
- Self-hosting is not automatically faster: "the Web Almanac found that sites using third-party fonts had a faster render than fonts that used first-party fonts… If you are considering using self-hosted fonts, confirm that your site uses a CDN and HTTP/2."

### 3.2 font-display, and CLS/FOUT/FOIT

[VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@font-face/font-display
- Values as periods: `block` = "short block period and an infinite swap period"; `swap` = "extremely small block period and an infinite swap period"; `fallback` = "extremely small block period and a short swap period"; `optional` = "extremely small block period and no swap period"; `auto` = UA-defined (initial value `auto`).
- Period definitions: block period → "must render an **invisible** fallback font face" (that is FOIT); swap period → fallback is visible and the web font is swapped in if it lands (that is FOUT); failure period → "treats it as a failed load causing normal font fallback".
- UA timing knobs (Firefox): `gfx.downloadable_fonts.fallback_delay`, `gfx.downloadable_fonts.fallback_delay_short`. Spec: CSS Fonts Level 4.

[VERIFIED-fetched] https://web.dev/articles/font-best-practices — concrete numbers and the UX verdicts:
- Browser default blocking: "By default, Chromium-based and Firefox browsers block text rendering for up to 3 seconds if the associated web font has not loaded. **Safari blocks text rendering indefinitely.**"
- Table: Auto = varies/varies; Block = 2–3s / infinite; Swap = 0ms / infinite; Fallback = 100ms / 3s; Optional = 100ms / none.
- Three priority-led choices: performance → `optional` ("text render is delayed for no longer than 100ms and there's assurance that there isn't font-swap related layout shifts. The downside is that the web font won't be used if it arrives late"); fast text with a web font → `swap` "but make sure to deliver the font early enough that it does not cause a layout shift"; guaranteed web-font first paint → `block` "but make sure to deliver the font early enough" — with the sharp observation that `block` "can still cause a layout shift as the text is actually drawn invisible, and the fallback font space is therefore used to reserve the space."
- Mixing per role: "use `font-display: swap` for branding and other visually distinctive page elements. Use `font-display: optional` for fonts used in body text."
- **Discrepancy to resolve in the doctrine:** web.dev's CLS section advises "Preload fonts while using the default `block` value for `font-display`" as one of three strategies, while MDN states the initial value of `font-display` is `auto` and the spec's default UA behaviour is a block-ish period. Treat "`block`" as a value you opt into explicitly, not as "the default", and prefer the *combination* (preload + block) as the shift-free-but-slow option, `optional` without preload as the shift-free-and-honest option. [VERIFIED-fetched both, REASONED reconciliation]

[VERIFIED-fetched] https://web.dev/articles/preload-critical-assets — the crossorigin rule and the double-fetch penalty, verbatim: fonts "are loaded in anonymous mode. For those you must set the `crossorigin` attribute with `preload`" → `<link rel="preload" href="ComicSans.woff2" as="font" type="font/woff2" crossorigin>` and "**Fonts preloaded without the `crossorigin` attribute will be fetched twice!**" Also: "Omitting the `as` attribute, or having an invalid value is equivalent to an XHR request… can also cause some resources, such as scripts, to be fetched twice"; "Unused preloads trigger a Console warning in Chrome, approximately 3 seconds after the `load` event"; "If too many resources are prioritized, effectively none of them are"; WOFF2-or-LCP: "using older formats such as WOFF 1.0 or TrueType (TTF) will delay your LCP if the LCP candidate is a text node."

### 3.3 Variable fonts

[VERIFIED-fetched] https://web.dev/articles/variable-fonts
- One file replaces many styles: "Before variable fonts, each style was implemented as a separate font file. With variable fonts, all styles can be contained in a single file"; registered axes `wght`, `wdth`, `slnt`, `opsz`, `ital`.
- Load syntax with ranges and the variation `tech()`: `src: url('RobotoFlex-VF.woff2') format('woff2') tech('variations')` + the deprecated `format('woff2-variations')` twin line, `font-weight: 100 1000; font-stretch: 25% 151%;` — "By specifying the range in `@font-face`, any value outside this range will be 'capped' to the nearest valid value."
- Size economics are conditional, not universal: Monotype's 48-styles-in-one experiment gave "a *88% reduction in file size*", but "if you are using a single font such as Roboto Regular and nothing else, you might not see a net gain in font size if you were to switch to a variable font with many axes" (and web.dev's fonts page repeats: variable fonts "typically have larger file sizes than individual non-variable fonts").
- The `font-variation-settings` trap that *is* a rendering bug, not a perf note: "Every property you *don't explicitly set* will automatically be reset to its default. Previously set values aren't inherited!" → two classes each setting one axis cancel each other; documented workaround is CSS custom properties feeding one `font-variation-settings` declaration; and animating CSS variables doesn't work, so animations must target `font-variation-settings` directly.
- FOUT/FOIT angle: variable fonts don't change `font-display` semantics (they are still a single `@font-face` resource) — but because one file is bigger, the block/swap window is more likely to be visible, and Google Fonts' own API "will send static fallback fonts in case variable fonts aren't supported", with `@supports (font-variation-settings: normal)` as the progressive-enhancement split. [VERIFIED-fetched for the fallback/`@supports` and Google API behaviour; REASONED for the "bigger file ⇒ longer swap window" link]
- Perf hygiene: "animating the font between settings may cause performance issues… reduced somewhat by only animating fonts that are currently on screen" (IntersectionObserver + `animationPlayState`), and throttle/debounce interaction-driven axis changes.

### 3.4 Icon fonts vs SVG — the modern verdict

- web.dev states it directly: "The `font-display` strategies that work well for conventional web fonts don't work as well for icon fonts. The fallback font for an icon font typically looks significantly different than the icon font, and its characters may convey a completely different meaning. As a result, icon fonts are more likely to cause significant layout shifts. In addition, using a fallback font may not be practical. **When possible, replace icon fonts with SVGs, which is also better for accessibility.**" [VERIFIED-fetched] https://web.dev/articles/font-best-practices (it points at Font Awesome SVG sprites and the Material Icons SVG guide)
- Platform owners are moving: a live WordPress core Trac ticket proposes "Administration: Replace Dashicons icon font with…" SVG, listing among the defects "No built-in meaning: Icon fonts are just styled characters with no inherent description — accessibility has to be added manually." [SEARCH-asserted] https://core.trac.wordpress.org/ticket/65089
- Secondary, still-true reasons that icon fonts leak in practice [REASONED, each grounded above]: ligature/PUA glyphs are read aloud as garbage unless `aria-hidden` is perfect; text-scaling settings change icon size as if it were text (which is the *reason* the typographic sizing is nice, and also the bug); a partially-loaded icon font is invisible or tofu, and no `font-display` value fixes that honestly; and icon fonts are a whole extra font request in the critical chain that `@font-face` only fetches when referenced (§3.1).
- Where icon fonts still win: existing large native-app icon systems and CSS pseudo-element decoration where no markup node exists. [REASONED] Note that the browser-native icon systems (§6) are **not** icon fonts in the web sense — SF Symbols are vector images with text traits ("Although symbols are images, they support many traits you associate with text") and Android's are VectorDrawables. [VERIFIED-fetched]

### 3.5 Metric overrides: making the fallback lie convincingly

[VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@font-face/size-adjust — "defines a multiplier for glyph outlines and metrics associated with this font. This makes it easier to harmonize the designs of various fonts when rendered at the same font size… All metrics associated with this font are scaled by the given percentage. This includes glyph advances, baseline tables, and overrides provided by `@font-face` descriptors." Example is exactly the doctrine pattern: an `@font-face` with `src: local("Local Font"); size-adjust: 90%;`.

[VERIFIED-fetched] https://web.dev/articles/css-size-adjust — the why and the how:
- "By putting `size-adjust` in the `@font-face` rule, it sets a global glyph adjustment for the font face. Timing this right will lead to minimal visual change, a seamless swap." Named purpose: "optimizing web font rendering to prevent cumulative layout shift (CLS)".
- Two calibration strategies: **remote target** (adjust the local fallback toward the brand font — "The brand is the calibration target. This is great news for design systems") and **local target** (adjust the brand font to match Arial). Worked snippet:
  `@font-face { font-family: 'Adjusted Arial'; size-adjust: 86%; src: local(Arial); }` and the calculator output `@font-face { font-family: "Roboto-fallback"; size-adjust: 100.06%; src: local("Arial"); }`.
- Cross-platform hedging: declare two adjusted fallbacks (`local("Arial")` 100.06%, `local("Arimo")` 99.94%) and list them after the brand font, because "`local(Arial)` may not be available on all your user's devices, therefore it's important to provide multiple fallbacks in the font-family"; "The order of `font-family` is critical."
- Finer knobs: `ascent-override` ("defines the height above the baseline of a font", e.g. `ascent-override: 71%`), `descent-override`, `line-gap-override` — "currently implemented in Chromium 87+, and Firefox 89+" (Safari only in Technology Preview at the time of that doc), used when "generic scaling of glyphs isn't enough".

### 3.6 System font stack

- "A *system font* is the default font used by the user interface of a user's device. System fonts typically vary by operating system and version. Because the font is already installed, the font does not need to be downloaded. **System fonts can work particularly well for body text.**" Usage: `font-family: system-ui`. [VERIFIED-fetched] https://web.dev/articles/font-best-practices
- Doctrine conclusion [REASONED, from 3.1/3.5/3.6]: a custom font must be paid for. If the brand font is not load-bearing on the page, `system-ui` removes the download, the block/swap window, the CLS mitigation, the subsetting pipeline and the licence audit. If it *is* load-bearing, then WOFF2 + subset + metric-matched fallback + explicit `font-display` per role is the complete answer, and there is no shortcut where you get a custom font and zero shift risk for free.

## 4. Video and audio

### 4.1 preload, and the data/UX bill

[VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/video (`preload`)
- Values: `none` "the video should not be preloaded"; `metadata` "only video metadata (e.g., length) is fetched"; `auto` "the whole video file can be downloaded, **even if the user is not expected to use it**"; empty string is a synonym of `auto`.
- "**The default value is different for each browser. The spec advises it to be set to `metadata`.**"
- Precedence and limits: "`autoplay` attribute has precedence over `preload`"; "Videos with `loading="lazy"` will only apply the `preload` behavior once the video is near or within the viewport"; "The specification does not force the browser to follow the value of this attribute; it is a mere hint."

`loading` on `<video>` [VERIFIED-fetched, same page]: `eager` is the default; `lazy` "Defers loading the video until it reaches a calculated distance from the viewport… avoids the network and storage bandwidth required to handle the video until it's reasonably certain that it will be needed. This improves the performance in most typical use cases." Two sharp caveats: "**While explicit `width` and `height` attributes are recommended for all videos to avoid layout shift, they are especially important for lazy-loaded ones. Lazy-loaded videos will never be loaded if they do not intersect a visible part of an element, even if loading them would change that, because unloaded videos have a `width` and `height` of `0`. It creates an even more disruptive user experience when the content visible in the viewport reflows in the middle of reading it.**" And lazy loading is "an anti-tracking measure" and "only deferred when JavaScript is enabled". Also `loading="lazy"` suppresses autoplay until near-viewport, and defers the poster fetch too.

Doctrine [REASONED from the above]: default `preload="metadata"` + `loading="lazy"` + explicit `width`/`height` (or an `aspect-ratio` box) for anything below the fold; `preload="none"` only when the media is genuinely optional *and* you accept an empty player; `preload="auto"` only for the one video that is the page's primary content.

### 4.2 Poster, autoplay policy reality

- Poster: "A URL for an image to be shown while the video is downloading. **If this attribute isn't specified, nothing is displayed until the first frame is available**, then the first frame is shown as the poster frame." [VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/video → so a missing poster means an empty player box on slow networks and a blank surface for lazy-loaded videos, which is why "poster required" is a rule, not a nicety. [REASONED]
- Autoplay policy: "Autoplay blocking is *not* applied to `<video>` elements when the source media does not have an audio track, or if the audio track is muted. Media with an active audio track are considered to be **audible**, and autoplay blocking applies to them." Availability — autoplay allowed if at least one of: muted/volume 0; "The user has interacted with the site (by clicking, tapping, pressing keys, etc.)"; the site is allowlisted "either automatically if the browser determines that the user engages with media frequently" (= the engagement/Media Engagement Index route) or manually; or the autoplay Permissions Policy grants an iframe. "Otherwise, the playback will likely be blocked. The exact situations… and the specifics of how sites become allowlisted, vary from browser to browser." [VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay
- The recommended autoplay markup, verbatim: `<video src="/videos/awesomevid.webm" controls autoplay playsinline muted>` with the note "since the `muted` attribute is included, and **the `playsinline` attribute that is required for autoplay in Safari**, the video will autoplay but with the audio muted." [VERIFIED-fetched, same page] → this is the citation for "poster + muted + playsinline or it does not autoplay on mobile".
- Feature detection and failure handling: `navigator.getAutoplayPolicy("mediaelement")` → `allowed` / `allowed-muted` (mute it) / `disallowed` (fall back to a `poster`), with the caveat "there is no way to be notified when the autoplay policy has changed… generally we recommend that the policy is checked when the page is loaded, using the type"; and for `play()` — "When autoplay fails, you likely will want to offer a way for the user to manually tell the browser to ask the user to grant permission to play media", catching `NotAllowedError` and showing a play button. Also "It is strongly recommended that you use the `autoplay` attribute whenever possible" (over scripted play). Attribute-shape trap: `autoplay="false"` does **not** disable autoplay — "the video will autoplay if the attribute is there in the `<video>` tag at all. To remove autoplay, the attribute needs to be removed altogether"; same for `muted`. [VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay and https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/video
- `<playsinline>`: "A Boolean attribute indicating that the video is to be played 'inline', that is, within the element's playback area. Note that **the absence of this attribute does not imply that the video will always be played in fullscreen.**" [VERIFIED-fetched] video page.

### 4.3 Facades for embeds

[VERIFIED-fetched] https://web.dev/articles/embed-best-practices
- "A facade is a static element that looks similar to the actual embedded third-party but is not functional and, therefore, much less taxing on the page load."
- Cost framing: "Many popular embeds include over 100 KB of JavaScript, sometimes even going up to 2 MB"; "Lazy loading the YouTube embed can save approximately 500 KB on the initial page load"; Instagram "can be over 100 KB gzipped".
- The named tool: "**Lite-youtube-embed is a recommended facade for the YouTube player, which looks like the real player but is 224 times faster**", used as `<lite-youtube videoid="ogfYd705cRs" playlabel="Play: Keynote (Google I/O '18')">`; alternatives `lite-youtube`, `lite-vimeo-embed`, `lite-vimeo`; chat widgets via `react-live-chat-loader`.
- The escalation ladder: static-image facade → dynamic-image facade (Maps Static API / tweet screenshot) → "click-to-load", "also known as the *import on interaction* pattern": "1. On page load: Facade… 2. On mouseover: Facade preconnects to the third-party embed provider. 3. On click: The facade is replaced by the third-party product."
- Scope limit stated by the doc: "It's best to use the techniques described in this post to load only offscreen or non-primary page content. This ensures that all the critical content gets indexed by search engines." → doctrine: never facade the hero video if the video *is* the content.
- A11y/semantics for facades [REASONED, from the `playlabel` attribute and §1.7/§5]: a facade is a control — it must be a real `<button>` with an accessible name naming the *video*, keyboard-operable, and inside the reserved aspect-ratio box so the swap causes no shift.

### 4.4 Aspect-ratio containers to kill CLS

- MDN video, verbatim: "While explicit `width` and `height` attributes are recommended for all videos to avoid layout shift…" [VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/video
- embed-best-practices: "Layout shifts can be avoided by reserving space during page load for elements that are going to be dynamically loaded later… You can ensure this by specifying the `width` and `height` attributes of iframes or by setting a fixed size for static elements where the third-party embed will be loaded" (`<iframe … width="560" height="315">`), plus **Layout Shift Terminator**, which "Loads the embed client-side in an iframe. Resizes the iframe to various popular viewport sizes… generates media queries and container queries. Sizes a min-height wrapper around the embed markup." [VERIFIED-fetched] https://web.dev/articles/embed-best-practices
- `aspect-ratio` mechanics for the container: `aspect-ratio: 16/9` gives "the box's preferred aspect ratio"; **"At least one of the box's sizes needs to be automatic in order for `aspect-ratio` to have any effect"** — a container with both width and height fixed ignores it. `auto && <ratio>` = "When both `auto` and a `<ratio>` are specified together, `auto` is used if the element is a replaced element… Otherwise, the specified ratio… is used" → the correct pattern for a facade/placeholder is `aspect-ratio: 16/9` on the wrapper + `aspect-ratio: 16/9 auto` (or explicit intrinsic ratio) on the media child. [VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/aspect-ratio
- `object-fit`/`object-position` control "how the video's size is adjusted to fit within the frame" — the crop decision inside the reserved box. [VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/video

### 4.6 Audio autoplay and Media Session

- Audio is gated by the same audible-media rule (needs mute, prior interaction, allowlist/MEI, or Permissions-Policy), and Web Audio is included: "In the Web Audio API, a website or app can start playing audio using the `start()` method… Doing so outside the context of handling a user input event is subject to autoplay rules." Firefox additionally "block[s]-autopl… until after a tab is brought to the foreground" (`media.block-autoplay-until-in-foreground`, default `true`) and applies autoplay blocking to WebAudio by default (`media.autoplay.block-webaudio` default `true`). [VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay
- The gesture pattern, verbatim from the Media Session docs: "Some user agents disable autoplay for media elements on mobile devices and require a user gesture to start media", shown as a `pointerup` listener on a play button that calls `audio.play()` and only then sets up media-session controls. [VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/API/Media_Session_API
- Media Session API: "provides a way to customize media notifications… metadata for display by the user agent" plus "action handlers that the browser can use to access platform media keys such as hardware keys found on keyboards, headsets, remote controls, and software keys found in notification areas and **on lock screens of mobile devices**. So you can seamlessly control web-provided media via your device, even when not looking at the web page." Feature-detect `if ("mediaSession" in navigator)`, set `navigator.mediaSession.metadata = new MediaMetadata({ title, artist, album, artwork: […sizes…] })`, `playbackState = "playing"`, and register handlers (`play`, `pause`, `stop`, `seekbackward/forward/to`, `previoustrack`, `nexttrack`, `skipad`, `togglecamera`, `togglemicrophone`, `hangup`); wrap unsupported ones in `try/catch` (the doc's own pattern). Also "Since multiple pages may be simultaneously using this API, the user agent is responsible for calling the correct page's action handlers." [VERIFIED-fetched] same URL; deeper article: https://web.dev/articles/media-session (linked from MDN, not fetched)
- WCAG's audio obligation is separate from autoplay policy and stricter: **SC 1.4.2 Audio Control (Level A)** — "If any audio on a web page plays automatically for more than 3 seconds, either a mechanism is available to pause or stop the audio, or a mechanism is available to control audio volume independently from the overall system volume level", with the non-interference note "Since any content that does not meet this success criterion can interfere with a user's ability to use the whole page, all content on the web page… must meet this success criterion." [VERIFIED-fetched] https://www.w3.org/TR/WCAG22/

### 4.7 Lottie / Rive (animated vector graphics)

- What Lottie is: "Lottie is a mobile library for Web, and iOS, Android, React Native, and Windows that parses Adobe After Effects animations exported as json with Bodymovin and renders them natively on mobile!" Web load API: `lottie.loadAnimation({ container, renderer: 'svg' | 'canvas' | 'html', loop, autoplay, path | animationData })`. [VERIFIED-fetched] https://raw.githubusercontent.com/airbnb/lottie-web/master/README.md
- Payload and cost, from the maintainers: "**gzipping the animation jsons and the player have a huge reduction on the filesize. I recommend doing it if you use it for a project**"; "This is real time rendering. Although it is pretty optimized, it always helps if you keep your AE project to what is necessary… try not to use huge shapes in AE only to mask a small part of it. **Too many nodes will also affect performance**"; masks have "a huge performance hit" for inverted modes; `lottie.setQuality()` — "default 'high', set 'high','medium','low', or a number > 1 to improve player performance. In some animations as low as 2 won't show any difference"; `progressiveLoad` and `hideOnTransparent` are svg-renderer-only knobs; Safari mask bug needs `lottie.setLocationHref()` "when you experience mask issues in Safari… usually caused by usage of base tag in html"; and passing the same `animationData` object to `loadAnimation` repeatedly needs a deep clone for repeaters (#1159/#2151).
- Lottie a11y hooks exist natively: `rendererSettings: { title: 'Accessible Title', description: 'Accessible description.' }` — "Adds SVG title element for accessible animation title" — and the preview flow says take "an svg snapshot of the animation to use as poster… I recommend passing the svg through an svg optimizer like svgomg". [VERIFIED-fetched, same URL] → doctrine: a Lottie export ships with a poster SVG snapshot and a `title`/`description`, and `prefers-reduced-motion` is handled by pausing the instance (`pause()` / `freeze()` / `autoplay: false`). [VERIFIED methods; REASONED recommendation]
- Runtime weight is a separate bill from the file: the player bundle itself is counted by practitioners as "lottie-web at about 60–75 KB gzip, or dotlottie-web plus a ~500 KB WASM engine on first construct", i.e. the JS engine often dwarfs a single animation. [SEARCH-asserted] https://uithings.com/lottie-animations — **not authoritative; treat as an order-of-magnitude claim to measure locally.** dotLottie as the compressed container: "The dotLottie (.lottie) format zips the JSON and its assets to cut file size." [VERIFIED-fetched] https://rive.app/blog/rive-as-a-lottie-alternative (Rive's own comparison, so vendor-adjacent)
- Rive's claims (vendor, and Rive is the competitor — confidence accordingly): "A Rive file uses a compact binary format designed for runtime, and **Rive files are often 10 to 15 times smaller than equivalent Lottie JSON files**. Example: a 240KB Lottie animation was recreated in Rive at 16KB. CARS24 cut animation file sizes by up to 90% (from about 150KB to about 15KB)"; "The Rive Renderer draws on the GPU, using Metal on Apple platforms, OpenGL on Android (with Vulkan as an option in some runtimes), and WebGL2 on the web"; differentiators listed are state machines/interactivity, Data Binding, responsiveness, and scripting. [VERIFIED-fetched, vendor] https://rive.app/blog/rive-as-a-lottie-alternative → treat the ratio as plausible-but-self-serving; measure on your own assets. Independent practitioner comparison exists (Callstack's Lottie-vs-Rive mobile writeup: "Rive animation runs almost at 60FPS whereas Lottie runs at 17FPS") [SEARCH-asserted] https://www.callstack.com/blog/lottie-vs-rive-optimizing-mobile-app-animation
- Doctrine conclusion [REASONED]: animated *illustration* belongs in video (or CSS for tiny motions) far more often than in a runtime-parsed JSON player; choose Lottie/Rive when the animation must recolour with the theme, stay crisp at any DPR, and be interactive (state-driven), and budget for a runtime dependency plus a per-frame CPU/GPU cost that a `<video>` tag does not impose. Both require a reduced-motion plan and a static poster/snapshot fallback.

## 5. Motion and accessibility, across all media

- What the signal means: `prefers-reduced-motion` "is used to detect if a user has enabled a setting on their device to minimize the amount of non-essential motion. The setting is used to convey to the browser on the device that the user prefers an interface that **removes, reduces, or replaces** motion-based animations. Such animations can trigger discomfort for those with vestibular motion disorders. **Animations such as scaling or panning large objects can be vestibular motion triggers.**" Values: `no-preference` (evaluates false) and `reduce` (true; `(prefers-reduced-motion)` ≡ `…: reduce`). Also surfaced to servers as the `Sec-CH-Prefers-Reduced-Motion` client hint. [VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion
- The obligation levels, verbatim [VERIFIED-fetched] https://www.w3.org/TR/WCAG22/:
  - **2.2.2 Pause, Stop, Hide (A)**: "For moving, blinking, scrolling, or auto-updating information… For any moving, blinking or scrolling information that (1) starts automatically, (2) lasts more than five seconds, and (3) is presented in parallel with other content, there is a mechanism for the user to pause, stop, or hide it unless the movement… is essential." Note 2 makes it non-interference (applies to all content on the page), and Note 4 grants the preloader exception: "An animation that occurs as part of a preload phase or similar situation can be considered essential if interaction cannot occur during that phase for all users and if not indicating progress could confuse users…"
  - **2.3.3 Animation from Interactions (AAA)**: "Motion animation triggered by interaction can be disabled, unless the animation is essential to the functionality or the information being conveyed." (Glossary: motion animation = "addition of steps between conditions to create the illusion of movement or to give a sense of a smooth transition")
  - **1.4.2 Audio Control (A)**: >3 s of automatic audio needs pause/stop or independent volume.
  - **1.1.1 Non-text Content (A)** covers time-based media: "If non-text content is time-based media, then text alternatives at least provide descriptive identification", and Guideline 1.2 adds captions (1.2.2 A) / audio description (1.2.5 AA) obligations; MDN's video page operationalizes it: "Videos should provide both captions and transcripts… Captions should not obstruct the main subject of the video" and auto-generated captions must be reviewed. [VERIFIED-fetched] https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/video
  - Note the level asymmetry that matters for doctrine: "motion off" is **AAA**, while "auto-playing >5s moving content must be pausable" is **A** — so the practical, defensible bar is *controls for auto-play*, *`prefers-reduced-motion` handling as a quality obligation*, not as WCAG-A conformance. [REASONED from the verified levels]
- Concrete reduced-motion CSS shape from MDN: keep the animation, replace it with a non-vestibular one inside the query ("/* Tone down the animation to avoid vestibular motion triggers. */ @media (prefers-reduced-motion: reduce) { .animation { animation: dissolve 4s … } }") — i.e. **replace, don't only delete**, and put the reduced rule later in source order with equal specificity. [VERIFIED-fetched]
- Static fallback obligations per media type [REASONED, each grounded]: auto-playing muted `<video>` loop → poster frame + pause/stop control (2.2.2) and honor `reduce` by pausing and showing the poster (poster is already required by §4.2); GIF/APNG → the raster lane already covers "don't auto-play looped animation without control"; parallax/scroll-linked motion → disable the transform under `reduce` (SC 2.3.3 intent); Lottie/Rive → `autoplay: false` + `pause()`/`freeze()` and render the exported first-frame SVG snapshot (verified APIs: `pause`, `goToAndStop`, `freeze`, poster snapshot).

## 6. Native/mobile notes (one paragraph each)

**Android vector assets (VectorDrawable / AnimatedVectorDrawable).** Android 5.0 (API 21) "was the first version to officially support vector drawables with `VectorDrawable` and `AnimatedVectorDrawable`, but you can support older versions with the Android support library" (`VectorDrawableCompat`, `AnimatedVectorDrawableCompat`); the compat path requires opting in via `android { defaultConfig { vectorDrawables.useSupportLibrary = true } }` because AGP otherwise rasterizes at build time, and AppCompat's `app:srcCompat` is needed at some XML sites because "the way Android loads drawables, not every place that accepts a drawable ID, such as in an XML file, supports loading vector drawables". [VERIFIED-fetched] https://developer.android.com/develop/ui/views/graphics/vector-drawable-resources Versioning traps to encode in the doctrine: that same page says the support libraries let you target "all Android platform versions back to Android 2.1 (API level 7+)" and, four paragraphs later, "you can use `VectorDrawableCompat` and `AnimatedVectorDrawableCompat` on all devices running Android 4.0 (API level 14) and higher" — **an internal inconsistency in the official doc; verify against your own minSdk and the AndroidX release notes rather than trusting either sentence**, and note that `fillColor`/`fillType`/`strokeColor` need the compat layer below API 24. Animation mechanics: AVD targets `<group>` and `<path>` by `android:name` from `<objectAnimator>`s, and for morphing "the paths must be compatible for morphing: they must have the same number of commands and the same number of parameters for each command"; the single-file `aapt:attr` bundle form "requires Build Tools 24 or higher"; support-library-era extras are Path Morphing/Path Interpolation (25.4.0+) and "move along path" (26.0.0-beta1+). [VERIFIED-fetched] https://developer.android.com/develop/ui/views/animations/drawable-animation and the compat page. [REASONED] Practical read: an SVG→AVD import silently drops what the Android format cannot express, so the authored SVG and the shipped AVD are two different artefacts and need separate review; also `AnimationDrawable.start()` "can't be called during the `onCreate()` method of your Activity, because the AnimationDrawable is not yet fully attached to the window" (the classic "frame animation doesn't play" bug).

**Apple SF Symbols (and AVPlayer).** SF Symbols is Apple's icon system, not an accessory: "Symbol images give you a consistent set of icons… a vector-based shape that scales without losing its sharpness", with text traits (text styles, nine weights "corresponding to a weight of the San Francisco system font", Dynamic Type scaling, baseline alignment, four rendering modes monochrome/palette/hierarchical/multicolor, variants outline/fill/slash/enclosed, and variable rendering from iOS 16). The versioning traps are explicit and are the doctrine's point: "Symbol names may change between operating system versions and SF Symbols app releases, so you need to review your symbol usage when supporting new versions. Look for the deployment target when browsing the SF Symbols app and use the old name if you're backward deploying"; "If a symbol doesn't render in your app, use the SF Symbols app to search for the symbol name, and look for availability updates"; "If a variant doesn't exist for a symbol, the system uses the base symbol"; and "SF Symbols is only supported in iOS 13 and later. In your asset catalog you might have a symbol image named `gamecontroller`, and a fallback PNG asset named `gamecontroller`… Programmatically, you need to use `#available` to load assets appropriately." Also "Starting in iOS 16, symbols don't automatically render in monochrome mode when you don't specify a mode… If your app needs monochrome rendering for a symbol, use `preferringMonochrome()`". [VERIFIED-fetched] https://developer.apple.com/documentation/uikit/configuring-and-displaying-symbol-images-in-your-ui (read via the `.md` mirror the site offers for automated tools) → **conclusion: name↔asset coupling and OS-version availability make SF Symbols a versioned dependency; the custom-symbol pipeline (`Symbol Image Set`, `custom.` prefix, "Each method looks only for its designated image type, which avoids namespace collisions") is how you ship icons that must exist regardless of OS.** Related HIG page (not fetched): https://developer.apple.com/design/human-interface-guidelines/sf-symbols [SEARCH-asserted].
AVPlayer is the lazy-by-design half of iOS video: "A player is a controller object that manages the playback and timing of a media asset… play local and remote file-based media, as well as audiovisual media served using HTTP Live Streaming", it "manages the playback of only a single media asset at a time" (use `AVQueuePlayer` for a queue, `replaceCurrentItem(with:)` to swap); `AVAsset` "only models the *static* aspects of the media… and on its own, isn't suitable for playback", you need the dynamic `AVPlayerItem`. Readiness is *observed*, never assumed: `status` ("A value that indicates the readiness of a player object for playback"), `timeControlStatus` ("whether playback is in progress, paused indefinitely, or waiting for network conditions to improve"), `reasonForWaitingToPlay`, and `automaticallyWaitsToMinimizeStalling` ("whether the player should automatically delay playback in order to minimize stalling"), with `playImmediately(atRate:)` as the explicit non-waiting escape and `preroll(atRate:completionHandler:)` which "Begins loading media data to prime the media pipelines for playback" (and `cancelPendingPrerolls()`). Bandwidth and battery are policy knobs: `networkResourcePriority`, `audiovisualBackgroundPlaybackPolicy`, `preventsDisplaySleepDuringVideoPlayback`. [VERIFIED-fetched] https://developer.apple.com/documentation/avfoundation/avplayer → doctrine: on iOS, "preparing" and "loading" are separate, asynchronous, observable states; a lazy grid of players should create items, observe `status`, and only preroll what is about to appear — the web analogue (`preload="metadata"` + `loading="lazy"`) has no synchronous equivalent.

**Android Media3/ExoPlayer lazy behaviour.** The official framing of the default is: "Traditionally, a video player only starts its work — connecting, downloading, parsing, buffering — after the user has chosen an item for playback. This reactive approach is slow for today's short form video context. The solution is to be proactive." Two graduated APIs: `player.preloadConfiguration = PreloadConfiguration(targetPreloadDurationUs = 5_000_000L)` for predictable playlists ("the player tries to preload five seconds of media for the next item in the playlist"; disable with `PreloadConfiguration.DEFAULT`), and `DefaultPreloadManager` + `TargetPreloadStatusControl` for feeds/carousels, where you return per-distance stages — `PreloadStatus.specifiedRangeLoaded(5000L)`, `TRACKS_SELECTED`, `SOURCE_PREPARED`, or `null` ("All other items are too far away") — and playback is handed the already-prepared source via `preloadManager.getMediaSource(mediaItem)` before `player.prepare()`/`play()`. Two cost-control rules are stated: "**Preloading is only started when no media is being loaded for the ongoing playback, which prevents it from competing for bandwidth with the primary playback**", and lifecycle hygiene — "it's recommended to release the manager before the player" (and Part 2 flags "using a sliding window to avoid memory issues"). Also "PreloadManager can keep both the previous and next items preloaded, whereas the PreloadConfiguration will only look ahead to the next items." [VERIFIED-fetched] https://developer.android.com/blog/posts/elevating-media-playback-introducing-preloading-with-media3-part-1 → doctrine: Android's "lazy" default is *zero* network until prepare, and preloading is an explicit, prioritized, bandwidth-yielding opt-in — the mirror image of the web's `preload="auto"` where the browser may download the file without being asked.

## 7. Cross-cutting rules the doctrine should state (synthesis)

1. **A vector's geometry contract is `viewBox` + `preserveAspectRatio`; its clipping contract is `overflow`.** Crop, resize, and "logo cut off" bugs are decided by those three, in that order. Never let a build step delete `viewBox`; pin `removeViewBox: false` in the repo's SVGO config even though v4 defaults are safe. [VERIFIED §1.1, §1.2]
2. **Optimization is not sanitization.** SVGO's default preset does not run `removeScripts`/`removeStyleElement`; untrusted SVG must pass a real sanitizer (`setHTML()` / DOMPurify with `{svg:true}`) or be served only in image mode. And inline/`<object>`/`<iframe>` SVG executes scripts while `<img>`/`background-image` does not — that is the load-bearing security boundary. [VERIFIED §1.6]
3. **Accessible naming lives on the consumer, not the glyph**: `<img alt>` for images, `role="img"` + `<title>`/`aria-labelledby` for meaningful inline SVG, `aria-hidden` + a label on the button for icon buttons. SVGO's `removeDesc` default and the `aria-describedby`-beats-`<desc>` precedence are the two details that break this quietly. [VERIFIED §1.7]
4. **An icon set is one system or it is noise**: single canvas, single stroke weight, cap/join, minimum gap, and corner grammar (Lucide's musts), one grid family per context (24 default; 16/20 only where the slot demands it), plus size via tokens (`em`/`lh`/custom props) and colour via inherited `currentColor` — which is precisely why `<use>` sprites and icon fonts both fail teams that want per-part colour. [VERIFIED §1.5, §2.1, §2.2, §2.4]
5. **Fonts: earn the download.** WOFF2 only, subset by `unicode-range` per locale, declarations discoverable early (inline in `<head>`, or `preconnect crossorigin` for third-party), `font-display` chosen per role, and `size-adjust` + ascent/descent/line-gap overrides so the fallback occupies the same box. `preload` only for the critical face, always with `crossorigin`, and never alongside reliance on `unicode-range` (preload ignores it). [VERIFIED §3]
6. **Icon fonts are legacy.** The official performance doc says to replace them with SVG for layout-shift and accessibility reasons; a real CMS core is still open about it; the platform icon systems that replaced the idea are vector images with text traits, not fonts. [VERIFIED §3.4]
7. **Video: metadata + poster + reserved aspect-ratio box, autoplay only muted+playsinline, embeds behind facades.** Each of these has a direct citation; the exceptions are (a) the page's primary content, which is not lazy-loaded, and (b) search-indexability. [VERIFIED §4]
8. **Audio needs a gesture; native-feeling playback needs Media Session; WCAG 1.4.2 is the strict one.** [VERIFIED §4.6]
9. **Motion is a user preference, not a decoration.** `prefers-reduced-motion: reduce` means remove/reduce/**replace**; WCAG requires a pause control for auto-motion >5s (A) and only AAA requires disabling interaction motion — so "static fallback available" is the honest minimum for autoplaying video, GIF, parallax, and Lottie/Rive. [VERIFIED §5]
10. **Animated vector graphics carry a runtime bill.** Lottie's own README says gzip everything, node count and masks are the perf cliffs, quality is a knob, and the poster snapshot is the fallback; Rive's 10–15× size advantage is a vendor claim to measure. Budget for the player, not just the file. [VERIFIED §4.7]
