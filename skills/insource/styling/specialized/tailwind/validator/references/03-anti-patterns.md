# Anti-patterns — violations that survive code review

Each entry: the bad code, why a reviewer waves it through, the rule that catches it, and the module
holding the fix. Line-level detection commands are in `01-detection-methods.md`; the numbers below
are Pattern ids, cited as `Pattern N`.

Module paths from this file are `../../<module>/method.md`.

## Pattern 1 : The dynamic class that looked fine locally

```tsx
function Tag({ color }: { color: 'red' | 'blue' | 'green' }) {
  return <span className={`bg-${color}-100 text-${color}-800 px-2 py-1`} />
}
```

**Why it passes review** — it renders in development, where the dev server scans rendered DOM and the
class happens to have been generated by another component. TypeScript narrows `color` to three
values, so it looks exhaustive. The reviewer assumes Tailwind sees what the code says.

**Caught by** R-01 (Error, Method 2). Tailwind's scanner reads source text, not runtime values: in a
production build no CSS is emitted and the tag arrives unstyled.

**Fix** `../../dynamic-classes/method.md` — a literal map holding complete class strings:

```tsx
const STYLES = {
  red: 'bg-red-100 text-red-800',
  blue: 'bg-blue-100 text-blue-800',
  green: 'bg-green-100 text-green-800',
} as const
function Tag({ color }: { color: keyof typeof STYLES }) {
  return <span className={`${STYLES[color]} px-2 py-1`} />
}
```

## Pattern 2 : The Vue component that still builds after the upgrade

```vue
<style scoped>
  h1 { @apply text-4xl font-bold text-zinc-900; }
</style>
```

**Why it passes review** — the same file built for a year under v3, and the v4 upgrade diff does not
touch it, so it is not in the PR to review. The failure surfaces only when that SFC is compiled.

**Caught by** R-02 (Error, Method 3). Under v4 a bundled-adjacent stylesheet has no access to theme
variables, custom utilities, or custom variants defined in other files.

**Fix** `../../config/method.md` — `@reference "../app.css";` inside the block, or skip `@apply` and
use the generated variable (`color: var(--text-zinc-900);`), which is faster and needs no directive.

## Pattern 3 : The `safelist` that survived the migration

```js
// tailwind.config.js, kept after the v4 upgrade
module.exports = {
  safelist: ['bg-red-500', 'bg-blue-500'],
}
```

**Why it passes review** — v4 ignores the key silently. No warning, no error, and the classes may
still be emitted because they appear elsewhere in the source, so the bug is invisible until the one
dynamic case that needed them regresses.

**Caught by** R-03 (Warning, or Error when no `@config` loads the file at all — Method 4).

**Fix** `../../migration/method.md` — `@source inline("bg-red-500 bg-blue-500");` in the CSS entry,
then delete the JS key.

## Pattern 4 : The `corePlugins` ban nobody has

```js
module.exports = {
  corePlugins: { float: false, clear: false },
}
```

**Why it passes review** — the team believes floats are banned project-wide. v4 has no
`corePlugins`, so the ban evaporated on upgrade day. Six months later a `float-right` lands and the
linter that was never written stays quiet.

**Caught by** R-03 (Warning, Method 4).

**Fix** `../../migration/method.md` — move the enforcement to a lint rule over the class string, or
exclude the drifting paths with `@source not`. Accept the loss explicitly and record it; silence is
the worst outcome.

## Pattern 5 : The border that used to be gray

```tsx
<div className="border rounded-lg p-4">
  <h2 className="font-bold">Card</h2>
</div>
```

**Why it passes review** — under v3 the default border colour was `gray-200`. v4 switched the default
to `currentColor`, so the same markup renders black. The reviewer spots it, calls it a one-off, fixes
that component, and the other four hundred bare `border` usages stay.

**Caught by** R-06 (Info, Method 7) — including the global-restore suppression, so a project that
already fixed it centrally is not nagged per call site.

**Fix** `../../migration/method.md` — per-site `border border-zinc-200`, or once:

```css
@layer base {
  *, ::after, ::before, ::backdrop, ::file-selector-button {
    border-color: var(--color-gray-200, currentColor);
  }
}
```

Same shape covers `divide-*`; the ring case is `@theme { --default-ring-width: 3px;
--default-ring-color: var(--color-blue-500); }`, and placeholders need an explicit
`placeholder:text-*`.

## Pattern 6 : The unlayered component class

```css
.card {
  border-radius: 1rem;
  padding: 1rem;
  background: var(--surface);
}
```

**Why it passes review** — the class exists, is used, and looks like any other stylesheet. Nobody
reads the file as "one that Tailwind was never told about". A consumer adding `p-4` to the same
element then wins or loses depending on import order, and the fix gets applied at the call site with
`!important`.

**Caught by** R-04 (Warning, Method 5).

**Fix** `../../config/method.md` — `@utility card { … }` under v4 so Tailwind sorts it against the
utilities that fight it; `@layer components` under v3 (and legacy-legal under v4).

## Pattern 7 : The ternary chain that should be a map

```tsx
function Button({ variant }: { variant: 'primary' | 'secondary' | 'danger' }) {
  return (
    <button className={
      variant === 'primary'
        ? 'bg-indigo-600 text-white hover:bg-indigo-700'
        : variant === 'secondary'
        ? 'bg-zinc-200 text-zinc-900 hover:bg-zinc-300'
        : 'bg-red-600 text-white hover:bg-red-700'
    } />
  )
}
```

**Why it passes review** — every branch is a complete literal string, so Tailwind emits all of it and
R-01 is correctly silent. It is only ugly, so it clears the bar. It then grows a fourth branch that
forgets `hover:`.

**Caught by** R-08 (Info, Method 8).

**Fix** `../../design-system/method.md` for where the variant set is defined and
`../../utility-soup/method.md` for the duplicated utilities across branches:

```tsx
const VARIANTS = {
  primary: 'bg-indigo-600 text-white hover:bg-indigo-700',
  secondary: 'bg-zinc-200 text-zinc-900 hover:bg-zinc-300',
  danger: 'bg-red-600 text-white hover:bg-red-700',
} as const
function Button({ variant }: { variant: keyof typeof VARIANTS }) {
  return <button className={VARIANTS[variant]} />
}
```

One key per state, complete class string per value, prop typed to the key union — a missing variant
becomes a type error instead of a silent fallthrough.

## Pattern 8 : The merge with the override in front

```tsx
function Panel({ className }: { className?: string }) {
  return <div className={twMerge(className, 'p-4 bg-white rounded-lg')} />
}
```

**Why it passes review** — "prop first, defaults after" reads like a natural argument order, and it
is the natural order for a plain joiner. For `twMerge` it is exactly backwards: the last occurrence of
a conflicting utility wins, so the component's own defaults override whatever the consumer passed,
and the prop is dead code.

**Caught by** R-09 (Info, Method 9) — reported as a shape, never as a verdict, since only the author
knows which side was meant to win.

**Fix** `../../utility-soup/method.md` — defaults first, consumer override last:

```tsx
<div className={twMerge('p-4 bg-white rounded-lg', className)} />
```

## Pattern 9 : The plugin that works on the author's machine

```js
const plugin = require('tailwindcss/plugin')

module.exports = plugin(function ({ matchUtilities, theme }) {
  matchUtilities({ tab: (v) => ({ tabSize: v }) }, { values: theme('tabSize') })
})
// no second-argument config
```

**Why it passes review** — the author's own project already sets `theme.extend.tabSize`, so the
utility works in every demo, screenshot, and test. A consumer who installs the plugin without that
namespace gets `values: undefined` and zero generated classes. No error, no warning, no CSS.

**Caught by** R-10 (Warning, Method 10).

**Fix** (this module owns it — no sibling covers plugin authoring): ship the defaults with the plugin.

```js
module.exports = plugin(
  function ({ matchUtilities, theme }) {
    matchUtilities({ tab: (v) => ({ tabSize: v }) }, { values: theme('tabSize') })
  },
  { theme: { tabSize: { 1: '1', 2: '2', 4: '4', 8: '8' } } }
)
```

Under v4, most small plugins do not need to be plugins: one `@utility` block plus `@theme` variables
in CSS is the same feature with no JS and no consumer configuration.

## Pattern 10 : The variant stack that compiles and lies

```tsx
<ul className="space-y-2 first:*:pt-0 last:*:pb-0">
  {items.map((item) => <li key={item}>{item}</li>)}
</ul>
```

**Why it passes review** — the class is valid syntax under v4, the upgrade codemod leaves it alone,
and the visual delta is one item's top padding. A reviewer who has not internalised the ordering change
cannot see a problem.

**Caught by** R-05 (Warning, Method 6).

**Fix** `../../migration/method.md` — v4 reads a stacked variant list left to right, so the child
variant comes first:

```tsx
<ul className="space-y-2 *:first:pt-0 *:last:pb-0">
```

Order matters only for variants that shape the selector (`*`, `has-[…]`, compound marker variants such
as `prose-headings:`). Media and plain state variants commute, and reporting them is a false positive.

## Report anti-patterns

The validator itself has failure modes; they are the reason the format is fixed.

| Anti-pattern | Consequence | Instead |
|---|---|---|
| Silently picking a version when the signals conflict | the version-gated rules switch off and the report reads clean | `[ERROR] R-00` first, then continue on the `package.json` state |
| Gating CI on Warning/Info | one unavoidable Info, and the step is disabled forever | gate on `^[ERROR]` only, and only when the team opts in |
| Reporting a grep hit without reading the block | `Pill.tsx`-style correct code gets filed as R-01, trust dies | the command generates candidates; the agent files findings |
| Fixing the code while reporting it | an unreviewed, unrequested diff, and the counts stop meaning anything | report; the cited module is where the edit happens |
| Citing a rule id with no module path | the reader has nowhere to go | every finding carries `Cite : ../<module>/method.md` |
| Folding R-08 into R-01 because both touch one function | an Error buried under an Info, or the reverse | one finding per rule, per line |
