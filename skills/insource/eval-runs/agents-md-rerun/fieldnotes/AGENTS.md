# Tidepool - Agent Rulebook

This file is a rulebook: it states what agents must do and must read in Tidepool. It does not
describe the system - the docs it points to do that. Follow it on every task, including work
delegated to subagents.

## 1. Agent Instructions

Stable behavioral rules, independent of version, channel, or task.

- Rules live here; explanations of how anything works live in `docs/` - if a paragraph describes,
  it belongs there; if it obligates, it belongs here.
- One owner per fact: touching another section's subject writes a brief + "see section N" or
  "Read: docs/...", never a restatement.
- Do not contradict a doc under `docs/` without verifying against the code first; when code and
  doc disagree, report the disagreement - never silently pick a side.
- Never invent a project fact that the interview and `docs/decisions/` do not establish: ask, or
  write it as a visible assumption - never a silent guess.
- State which skill you used when reporting results (section 10).

## 5. Agent Execution and Startup

Before the first change of a session:

1. Read this file and the section 2.2 mandatory docs.
2. Confirm active context: current branch and dimensions against section 2.1 (`git status` is a
   read-only act, always allowed - section 12).
3. Implementation tasks run the section 2 units check before writing code.
4. Tasks touching money or schema go through section 13's Exact rule before any edit.

Subagents do not start here - they start from the 6.4 block, which binds the whole rulebook to
them; this list is for the agent running a session.

## 6. Agents

### 6.1 Premise
A subagent sees no conversation and cannot ask - what its prompt lacks gets guessed; volatile facts travel as `<FILL>` slots and the whole rulebook travels with the worker.
### 6.2 Main-agent duties
- Name each subagent by responsibility (`money-math-reviewer`), never a generic label.
- Fill every `<FILL>` slot at paste time; supply complete context: goal, paths, decisions, deliverable.
- Bound the work: what it may touch, what returns as findings, what is out of contract.
- Reconcile report contradictions against the rulebook before acting on any of them.
### 6.3 Subagent duties
- The full rulebook binds you exactly as it binds the main agent; scope narrows ACTIONS, never
  OBLIGATIONS: no commits/VCS work unless ordered, no violations, no context leaks.
- Do only the scoped task; out-of-scope observations come back as findings, not changes.
- If the brief is impossible, say so with evidence and let the parent decide - never substitute a goal.
### 6.4 Baseline block - paste at the top of every subagent prompt
> Projection of the rulebook, not a second source: stable policy is fixed text, volatile facts are
> `<FILL>` slots the parent fills at paste time; regenerate when the rulebook changes.
```text
=== MANDATORY AGENT PREFERENCES (read and follow) ===
The whole rulebook binds you exactly as it binds the main agent; scope narrows ACTIONS, never
OBLIGATIONS - no commits/pushes/VCS state unless ordered, no violations, no context leaks.
1. CONTEXT - <FILL active version line>; <FILL active channel>; <FILL excluded paths> per 2.1; read <FILL docs from 2.2 + task docs>; indexes are routers, follow the links.
2. SKILLS - before any commit read docs/commit-craft.md (`commit` skill); never hand-edit docs/UNITS.md.
3. SHELL - one command at a time while investigating; chain only on true dependency; scratch under scratch/, delete after.
4. TOOLING - `uv` for Python, `bun` for JS only; other managers break uv.lock / bun.lock.
5. ENV - config only through AppSettings; never edit .env ad hoc; no direct os.environ reads.
6. DEBUG - reproduce on the local SQLite copy first; DB -> service -> UI; mutate only data/dev.sqlite; staging writes need a parent grant.
7. UNITS - read docs/UNITS.md before implementing; reuse/extend; propose an entry for any new unit.
8. REPORT - write .subagents/<name>.md when finished: goal, actions, files, decisions, verification.
9. PRIVACY - private paths (docs/drafts/, tools/, .subagents/) stay out of every artifact and commit.
10. RESOURCEFUL - everything project-local (uv .venv/, bun local installs); no global installs.
11. AUTHORITY - ask per session: external binaries, external processes, non-dev DB writes, credentials, machine config; if blocked, say what you cannot do and ask.
12. VCS - Git: inspect + local commits on feat/<slug> and beta allowed; push/PR/merge-to-main/tags ask; rebase/amend of pushed work, reset --hard, clean, force-push, --no-verify never;
    stash only as agent/<task-slug>; human identity + 14's disclosure trailer.
13. GOLDEN - config only via AppSettings (startup fails without it); money only integer cents through Money - a fractional amount is unconstructable.
14. FACTS - section 16's dated bullets win over your training memory.
15. VOICE - concise; match the user's register; reports inherit it.
16. SYNC - if your edit touches a block's meaning, update every linked location in the same change.
TASK-SPECIFIC DOCS: <master fills>
SCOPE: <what you may change; what you must not>
OUTPUT CONTRACT: <the exact deliverable, in the exact form>
=== END PREFERENCES ===
```

## 7. Privacy

Private paths - never commit, never quote in artifacts that leave the repo:

- `docs/drafts/` - working plans; `tools/` - local binaries, including `tools/sqlitebook.exe`.
- `.subagents/` - the cascade: a hidden tool hides its outputs, so every report and run artifact
  inside it is private too.
- Hidden binaries: the file never enters the repo; its install need is recorded in
  `docs/ARCHITECTURE.md`, not the artifact.
- Sync duty: every private path gets its line in `.gitignore` in the same change that declares it.
- A path tracked before the rule: ask the user before clearing the git cache
  (`git rm --cached`) - never delete silently.

## 8. Resourceful

**Project-local first** - dependencies, toolchains, interpreters, environments stay in the
project, in every language:

- Python: the repo's `uv`-managed `.venv/`; run through `uv run ...` so the pinned version is the
  version used.
- JS: `bun install` into the workspace's local `node_modules`; run via `bun run` / `bunx`.
- Global installs: exceptions named here, with reason - none recorded yet; nothing global gets
  installed without asking (section 9).

## 9. Authority

Default: ask per session before anything reaches outside the project's own scope.

| Action | Setting |
|---|---|
| Install a binary outside the project | ask per session |
| Run external processes | ask per session |
| Write to an existing DB outside `data/dev.sqlite` | ask per session |
| Read or write credentials | ask per session |
| Change machine-level config | ask per session |

- Project-local installs are section 8's rule and do not ask.
- When a limit blocks the work, say honestly what cannot be done, what it costs, and ask - never

## 12. Git

What the agent may do against this repo, and under whose name.

- **Allowed:** inspecting history and state any time (`status`, `log`, `diff`, `show`); local
  commits on `feat/<slug>` and `beta` per the section 3 branch model.
- **Ask first:** anything outward - push, PR creation, merges into `main`, branch deletion,
  release tags.
- **Never without explicit order:** rebase/amend of pushed commits, `reset --hard`, `git clean`,
  force-push, and never `--no-verify` - fix the failing hook's cause instead of bypassing it.
- **Parked work (stash):** allowed only patterned: `git stash push -u -m "agent/<task-slug>"`; in
  a shared worktree apply the exact entry by message, never a bare `pop`; drop only entries this
  agent created.
- **Change identity:** commits keep the repository's configured human identity; agent involvement
  is disclosed with `Co-authored-by: Tidepool Agent <agent@tidepool.local>`. Never edit git config.
  The commit/branch skills look for this line and defer to it.

## 13. Ambiguity

The standing policy for how the agent asks, and how what it decides gets recorded.

- **Question mode:** Broad by default - the user answers intent; mechanisms and internals are the
  agent's call, best-for-project.
- **Exact list (user-named, never moved silently):** storage-schema changes and anything touching
  money math. Ask these with concrete options, consequences, and a recommendation.
- **[MANDATORY] Ask while the user is in the loop whenever a decision carries weight:**
  irreversible, costly, security, cross-module, or product-behavior-changing. Its twin: trivia
  (naming, placement, routine internals) is decided, never asked.
- Consequential asks present each option with its downside; a dangerous option is labeled, never
  buried mid-list.
- **Before going anonymous** - any mode that takes the user out of the loop (delegated runs,
  autonomous hand-offs; the condition is "nobody is watching", never one skill's name): every
  critical open question gets asked
  first; leftovers become explicit written assumptions with their cost - never silently filled.
- **Decision records - this section owns the convention:**
  - One file per decision at `docs/decisions/<slug>.md`; a combined `decisions.md` is forbidden -
    it explodes with project age.
  - Header anchors: Date + Commit hash + App-Version + Status.
  - Content order: question -> context -> options (and why losers lost) -> choice -> consequences
    -> reversal boundary.
  - The ask-or-decide call itself gets a record, especially around anonymous runs.
  - Anonymous ledger: `docs/decisions/states.md` - resume reads it, hand-off writes it.
- Write the policy, never a transcript: no stored sample questions - only the kind of question and
  when to ask it.

## 14. Golden Rules

Never bend, whatever the task, deadline, or context. Each names its MECHANISM - the sanctioned
path plus the loud failure guarding it; a bare "don't" is vigilance, and vigilance rots.

- **Config values flow only through the typed schema.** Every value is declared in `AppSettings`
  (`services/api/settings.py`); startup fails fast on a missing or unknown key; no code reads
  `os.environ` directly - an import-linter gate enforces it in CI, so a violation is a build
  failure, never silent drift.
- **Money math happens only in integer cents through `Money`.** The float columns were dropped
  from the ORM model entirely - a fractional amount is unconstructable, not discouraged.

Two rules, under a screenful - a third joins only with a named mechanism.

## 15. Review

**Whenever a review runs - a named task below, or the self-review of your own diff - its first
pass is:** hunt violations of this rulebook - AGENTS.md itself, golden rules (section 14) above all,
then every other section - in the code AND in the docs. This is what "a review" means here; it is
not an always-on job between unrelated tasks (section 17's After gate covers ordinary work). A
clean scan while bugs exist means the scan was shallow.

Named tasks (name - what to read - what counts as a violation):

- **Docs** - the docs set end to end, every doc this file routes to - stale passages, docs nothing
  links to, any doc over 500 lines (it becomes a folder with an `index.md`).
- **DB** - every table in the SQLite database - hardcoded/mocked data the tables could answer,
  judged against section 14.

Full task bodies exceed this section's budget - keep the obligations here, read the complete
definitions: [docs/review.md](docs/review.md). Seeds, not a quota.

## 16. Facts

The bullets below are **verified facts that contradict what an agent's training or prior knowledge
would assume** about this stack. The rules of this section are fixed:

- These facts WIN OVER memory: if a bullet says X and you remember not-X, follow the bullet - your
  memory is older, and it was wrong here before.
- A suspect fact gets re-verified and re-dated, never argued from memory; if reality moved, update
  the bullet in place.
- Recording duty, for the life of the project: the moment verification during any task shows a
  prior belief wrong for this project, append a dated bullet in the same change - believed /
  actual / how it was proven.
- Format: `- **<subject>** - <the truth here>. Prior belief: <memory's claim>. Verified
  <YYYY-MM-DD> by <method>.` Bullets accumulate; none get pruned from memory.

- **SQLAlchemy 2.0-style `Mapped[]` annotations are required** - the legacy `Column()`-only style
  is not valid here. Prior belief: `Column()` style still works. Verified 2026-10-28 by mypy
  errors on the current pin.
- **SvelteKit form actions handle the invoice upload** - shipped through `+page.server.ts`; no
  hand-rolled endpoint exists. Prior belief: multipart needs a hand-rolled fetch endpoint.
  Verified 2026-10-30 by shipping the feature.

## 17. Before-Between-After

Always-on task rituals; the user's CURRENT prompt overrides a ritual for that task, and a standing
wish to change one edits this section (section 11's duty).

- **Before:** nothing beyond what sections 2 and 9 already cover - "read the mandatory docs
  first" is section 2 restated and does not live here; the phase stays empty until it earns a row.
- **While working:** before writing any new helper, search for an existing implementation and
  collapse the duplication mid-task - the section 2 check runs at the moment of writing, not only
  at planning.
- **After finishing:** run both gates - `bun run check` (svelte-check) and `uv run mypy
  services/api` - then self-review your own diff against the section 14 golden rules before
  calling the work done.

## 18. Voice

The register the agent speaks and writes in - [concise] (answer first, reasoning on request),
[explanatory] (trade-offs shown), [verbose] (teaching walkthroughs), [ponytail] (the lazy
senior dev: the shortest statement that still proves the point) - illustrative modes; the
choice belongs to the user. The user's own register (their vocabulary, directness, terseness)
sets the level answers are pitched at; questions are framed in their words.

- Agent voice: none recorded yet - the interview did not settle it; until chosen the agent
  keeps a neutral concise default and matches the user's observed register.

- Surfaces may carry different registers - replies to the user / public documents (README,
  release notes) / internal documents (decision records, reports): not yet split; one concise
  voice governs all surfaces until the user names per-surface registers.
- Written reflection: the same voice governs every document and artifact the agent writes -
  `.subagents/` reports, decision records, changelog and release prose. One voice, spoken and
  written.

## 19. Sync Blocks

Writable meanings with more than one home. Blocks sync in MEANING, not in letters - each home may
phrase per its idiom; drift of what they MEAN is the defect. An edit to one side's meaning updates
every row of that block in the same change (section 11); a moved anchor gets re-anchored there.

- **Format:** one table per block, rows exact: `location | line anchor | what this home carries`.
- **Where the tables live:** Read: [docs/sync-blocks.md](docs/sync-blocks.md) - one block today
  (version-declaration-sites); it grows one block per discovered pair, so it lives outside the
  rulebook on purpose.
