# Is this input already a prior denoise pass?

Run this check before diagnosing. Getting it wrong produces the specific bad outcome of patching something that was already reasoned through.

### Before diagnosing: check whether this input is already a prior denoise pass

The "crowded, noisy" diagnosis below assumes the input is an unexamined original. That assumption can be wrong, and silently proceeding as if it's always right produces a specific bad outcome: applying only small, incremental tweaks to something that's already well-structured, when what's actually needed is a real report back to the person that there isn't much crowding left to fix by the usual moves — and, separately, an offer to explore a *different structural direction or taste*, not a bigger dose of the same one. See `examples/rerun-detection.md` for this reasoned through on a full input, including where a generic-signals check is not enough on its own.

**Check the session's own history first — this is the most reliable signal and comes before anything else.** If this skill (or an equivalent redesign pass) already ran earlier in this same conversation, the input may *be* — in whole or in part — Claude's own prior output, even if it arrives as a fresh upload, a different filename, or only one file of a multi-file result the person isn't re-sharing in full. Before reasoning from generic signals, check: does any file, page, or section handed in now match, resemble, or plausibly descend from something already built earlier in this conversation? A page named "overview" appearing right after an Ultra pass built an "overview" page as its aggregate/dashboard page is not a coincidence needing generic-signal confirmation — it's the same artifact, and should be recognized as such directly. Don't wait to independently re-derive "this looks polished" from scratch when the conversation itself already answers whether it's prior output.

**Absent that, or in addition to it, recognize a prior pass from the input's own shape.** Signals include: a deliberate multi-step tonal ramp rather than ad-hoc colors, generous type/spacing already in place, content already redistributed onto a dashboard/overview separate from a detail page, promoted warning blocks, real depth/elevation, a consistent icon system — in short, the output shape this skill itself produces. Treat this as a real check to make on the actual input, not a formality to gesture at.

**When recognized, stop and report before building anything:**
1. Say plainly that the input already looks like it's been through an accessible-style pass (name the specific evidence — the ramp, the redistribution, the elevation system, or "this is the file I built earlier in this conversation" when that's what it is — briefly, don't just assert it).
2. Don't default to hunting for small residual crowding issues and patching them — that produces exactly the minimal-restructure, minimal-redesign outcome that under-delivers on a fresh request. If the mode requested is Ultra or Medium and the input is already clean, there usually isn't a "make it less crowded" job left to do in the usual sense.
3. Instead, explicitly offer to reapproach it from a **different structural direction or visual taste** — genuinely different choices, not a bigger version of the same ones already made. **Derive the options from this specific input, not from a stock list**: look at what's actually fixed about the current design (nav position, icon-vs-text density, card vs. list paradigm, tonal direction, information density) and for each, name the realistic alternative this particular product could take — a side-rail nav could become a top bar or a collapsible sliding panel *if* the input's own chrome-to-content ratio and navigation depth make that plausible; a text-label nav could go icon-first *if* the nav items are few enough and recognizable enough as icons; a warm/cool tonal direction could flip *if* the product's identity doesn't depend on the current one. Offering an alternative that doesn't fit this input's actual constraints (e.g. proposing icon-only nav for a screen with a dozen long, non-obvious nav labels) is worse than not offering one — it signals the options weren't actually derived from what's there. Ask which direction, if any, they want explored — this is a real fork in the work, not a detail to bury in the build.

4. **Before concluding "already done", check which half was done.** A prior pass now has a distinctive fingerprint: a real tonal ramp, redistributed tables, an elevation scale, a re-derived nav — and every form, dialog and state in the product still the original's, because the version of this skill that produced it had no moves for those surfaces. That input is not "already passed"; it is half-passed, and a generic signals check will read it as complete, which is how a genuinely needed rerun gets politely declined. Test it directly rather than by impression: count the writing surfaces and ask how many had controls re-ordered, re-grouped or re-containerised rather than repainted — `mode-audit.mjs` prints that ratio. If the answer is few or none, the specific evidence item 1 asks for is "the reading surfaces went through a pass; the writing ones never did", and the right offer is the missing half of the work, not a different taste.
4. Only proceed straight into a build without this stop-and-report if the person's own request already answers it — they named a specific new direction, said explicitly they know it's already been through a pass and want more of the same anyway, or said to just proceed.

**This interacts with mode selection (workflow step 1), not just diagnosis.** Asking "which mode — Lite, Medium, or Ultra" to a person whose input already went through an Ultra pass is a different question than asking it of someone with a genuinely crowded original — the honest framing at that point is closer to "this already got a full pass; do you want a lighter refinement, or a genuinely different take at the same intensity," and the direction-offer above is what fills in what "a genuinely different take" could mean. Fold the two together in one message rather than asking about mode first and surfacing the prior-pass finding as a separate, later interruption.

This check is separate from, and comes before, the type/spacing re-run note above — that note covers what to do about *scale* specifically once work is already underway; this one covers whether to stop and reframe the whole request before starting.
