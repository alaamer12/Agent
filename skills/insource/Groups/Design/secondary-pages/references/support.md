# Support / Help

The operational truth of getting help: where, how fast, in which languages, with what escalation.
Needed when the product has accounts or complexity enough that "contact us" is not a plan; for a
one-page tool it is over-engineering - the contact page suffices.

## Must include

1. **The self-help layer first** - docs/guides index (the project's real docs, linked not
   duplicated), the `faq.md` route, search.
2. **Ticket/live channels** - which exist (email, in-app, chat), their hours (ASK), and what
   "submitted" actually guarantees.
3. **Response windows** - per severity: account-lockout ≠ feature-suggestion; the table is the
   promise, and only the team's real number belongs in it.
4. **What makes a ticket fast** - the triage checklist (account, device/OS, steps, screenshots,
   when it started) - mirrors `contact.md`'s line, same source.
5. **Status and incidents** - `status.md` link ("something down? check here first").
6. **Language coverage** - honestly stated; an unanswered "we support ar/en" template line is a
   fabrication.
7. **Where support does NOT go** - billing disputes (the refund route), security reports
   (`security.md`), legal notices (`takedown.md`) - the routing table that stops tickets dying in
   the wrong queue.

## Writing professionally

- Support copy is written to be forwarded: short numbered steps, no brand voice when a machine is
  broken.
- The windows here are the same numbers `contact.md` and any SLA cites - one owner: a shared
  config/decision, everywhere else linked.

## Ask the user - never invent

Actual channels and tools (a form that creates nothing in any tracker is the classic
fabrication); hours and timezone coverage; severity windows; who reads the queue; languages.
