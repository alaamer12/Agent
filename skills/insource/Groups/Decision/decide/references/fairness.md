# Fairness and data discipline

## Winners and ties
- Several candidates can share first place. Treat first place as a tier, not a seat.
- Call a tie when the gap is within noise: overlapping ranges, a difference under what a user would notice, or evidence from sources that disagree. Show co-winners on the winner line and say why in the margin text.
- Only name a "clear margin" winner when independent evidence shows a gap that is large and consistent.

## Rating (shown on the candidate chips)
1. For each dimension assign tiers: best tier = 5, next = 4, next = 3, lower = 2, worst = 1. Ties share a tier.
2. Rating = average of tier points over the dimensions, equal weights, shown as `x.x/5`.
3. If the user states priorities, weight the dimensions as stated and say so under the chips, and show the equal-weight rating beside it so the effect is visible. Otherwise state "equal weights".
4. Label the rating as derived from the ranking table, not measured. Show the tier table on the page so it can be checked.
5. A candidate with no data for a dimension is marked "no data" and excluded from that dimension's average. Do not assign it a low tier by default.

## Same effort for every candidate
- Research each candidate to the same depth, including any the user seems to prefer.
- Give every candidate its strengths and its weaknesses. Do not leave a candidate out of a dimension without saying why (for example, "no figure found").

## Evidence
- Use only supplied or found data. Never use memory for figures, versions, dates or code.
- Cite a source for each claim or group of claims. If a claim has none, mark it unverified on the page.
- Grade sources: independent benchmark or official documentation > reproducible third-party test > vendor claim or blog opinion. Say which grade a key figure has when it matters.
- Show conflicts. If sources disagree (numbers, versions, status), show both and say so. Do not pick silently.
- Quote ranges as ranges. Collapse to one number only in a chart, and then say it is the midpoint.
- Check freshness. The page states the date of the comparison and the period the data covers in its own freshness section (see `page-structure.md`). Set the re-check date from how fast this domain changes (for example sooner for [fast-moving libraries] or [prices], later for [mature standards]). Flag anything that could already be stale.

## Wording
- Every comparison point needs a "why it matters" line that tells the user when the difference would affect them.
- Report real differentiators, not features everyone shares or what each vendor advertises.
- Neutral tone. No hype words. Short sentences.
- Do not say a candidate "is best". Say what it is best for.

## Verdict
- Pick per use case. If two candidates are effectively tied for the user's goal, say so and name what would tip the choice (a constraint, a team skill, a risk).
- End with the dominant constraint the user should decide on, not a single benchmark.
