# The `bequest` directory — layout, cards, discovery

One convention, so agent N+1 does not have to guess. The directory sits at the **project root**, is committed
with the repository, and contains nothing that only made sense during one conversation.

## Structure

```text
bequest/
├── INDEX.md                        the discovery surface: one row per asset
├── find-slow-requests/             one directory per asset (kebab-case)
│   ├── README.md                   the asset card (never optional)
│   ├── find_slow.py
│   └── tests/
│       ├── test_find_slow.py
│       └── fixtures/{slow.json,empty.json,broken.json}
├── pg-lock-check/
│   ├── README.md
│   └── lock_check.sql
├── restart-api-safely/             a procedure: the card IS the asset
│   └── README.md
└── nextjs-15-async-params/
    ├── README.md
    └── check_params.py
```

Rules that keep it usable:

- **Directory per asset**, even for a single file. The card needs somewhere to live.
- **Some assets are card-only** — a procedure, a pattern, a documented constraint. That is a complete asset: the
  steps, preconditions, verification and limitations are the deliverable. Do not invent a script to make it look
  technical.
- **Scripts, card and tests together.** When there *is* code, an asset is not its script; it is the script plus
  the knowledge of how to trust it.
- **No empty directories**, no `misc/`, no `old/`. If something is superseded, mark it in its card and point to
  the successor; do not accumulate `v1`, `v2-final`.
- **No large binaries** (dumps, videos, datasets). They belong in an artifact store; the card links to them.
- Size guide: if an asset needs more than ~10 files, it is probably a project module, not a bequest.

## `INDEX.md`

Two tables — scripts/utilities, then procedures/docs — or one table with a Type column. One row per asset:

| Asset | Type | What it does | Verification | Path |
|---|---|---|---|---|
| find-slow-requests | script | flags rows above a latency threshold in a JSON export | verified (manual) | `find-slow-requests/` |

The row's wording is the card's first sentence, so the index can be regenerated by reading cards. Keep it
sorted by name; a stale row is worse than no row (the validator checks both directions).

## The asset card — required sections

Exactly these headings, in this order (the validator enforces the set):

1. **What it does** — one sentence, behaviour only.
2. **When to use it** — the situation that should make an agent open this asset; include the trigger words.
3. **How to use it** — the exact command(s), copy-pasteable, plus `--help` semantics.
4. **Inputs** — each argument/env var: name, type, default, required?
5. **Outputs** — files, stdout shape, exit codes.
6. **Dependencies** — runtime, tools, versions, network access, privileges.
7. **Assumptions and limitations** — data shape, OS, scale, what was not implemented.
8. **Verification** — the status word, the commands run with observed results, what was not tested.
9. **Origin** — optional but useful: the session or incident it came from, and the date.

Template: [`../assets/templates/asset-card.md`](../assets/templates/asset-card.md).

## Update, don't fork

| Situation | Do this |
|---|---|
| The same problem came back with new cases | extend the existing asset and its tests; update the card's verification block |
| The old asset was wrong in a way that matters | fix it in place; note the change in the card's Origin line |
| A genuinely different approach is needed | create a new asset, and mark the old card `Superseded by <slug>` at the top |
| Two assets now do the same thing | merge into one, keep the better name, delete the loser after the index is updated |

The validator flags byte-identical duplicates; near-duplicates are a judgment call — prefer merging.

## Git and secrets

- **Committed.** Assets are project knowledge; they travel with the code and are reviewed like code.
- **No credentials, tokens, personal emails or internal hostnames.** Placeholders only (`<API_KEY>`,
  `example.internal`). If an asset needs a secret, the card says where it comes from, not what it is.
- **No machine paths.** `--input` arguments, relative paths, or a documented environment variable — never
  `C:\Users\…` or `/home/…`.
- **No session state.** Scratch files, logs and working notes do not belong here (they belong to `flush`, the
  incident folder, or nowhere).

## Discovery — how the next agent finds it

1. `bequest/INDEX.md` — the one-glance surface; read this first, always.
2. The candidate asset's `README.md` — decide whether it fits *this* task (inputs, assumptions, verification).
3. Its tests — run them before trusting the asset, especially if the status is `partially verified`.
4. Its code — only when the card is not enough.

That order is the contract with [`heir`](../../heir/SKILL.md): the consumer skill opens the index, then the card,
then runs the tests — and never edits an inherited asset without updating its card.
