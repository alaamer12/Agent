# The body: what and why, not how

The diff is the *how*. The body exists only for information the code cannot carry: motivation, the
alternative that was rejected, the constraint that made this the right choice, and the risk that was accepted.

## When a body is required

| Change | Body? |
|---|---|
| typo, rename, formatting, dependency bump with no behavior effect | no |
| anything a reviewer would question in review | yes |
| anything that fixes a defect | yes - the cause belongs somewhere permanent |
| anything with a trade-off, a caveat, or a follow-up | yes |
| anything that changes a public contract | yes, plus the `BREAKING CHANGE:` trailer |
| anything where the next reader will run `git blame` and ask "why is this here?" | yes - that body is the answer they came for |

Rule of thumb: if explaining it would take you two sentences in a code review, those sentences are the body.

## Structure that works

```text
<paragraph 1: what is now true, and the problem that made it necessary>
<paragraph 2: the approach and why it was chosen; the alternative rejected and when it would win>
<paragraph 3: consequences, caveats, follow-ups, measurements>
```

Three short paragraphs, blank line between them, wrapped at 72. No heading markup, no emoji, no markdown
tables - messages get read in terminals, in email patches, and in `git log` panes where markdown is noise.

## Good bodies, by case

A bug fix, where the cause is the valuable part:

```text
The retry loop re-sent webhook payloads on every 5xx, including 501 and 503,
which the upstream treats as permanent failures. Retrying those kept the queue
hot and delayed the real delivery by minutes.

Only 429, 502 and 504 are retried now, honoring Retry-After when present. The
permanent-failure path still records the delivery as failed for the dashboard.

Rejected: a global backoff - it fixed the symptom and kept retrying work that
could never succeed.
```

A refactor that should have no behavioral effect:

```text
Extracted tax rounding out of the checkout handler into a pure function so the
currency rules can be unit-tested without building a cart.

No behavior change intended; every call site keeps its current inputs. Two
rounding differences in the legacy path were left deliberately, marked with a
TODO each - they need a product decision, not a refactor.
```

A decision with an accepted cost:

```text
Switched the export from a streaming response to a temporary file plus a signed
URL. The stream kept dying on proxies that buffer, and support could not
reproduce it locally.

Cost: exports now live in object storage for 24h, and the delete sweep is a new
failure mode - covered by the hourly reconciliation job, which will log and
alert rather than fail silently. The user-visible download button is unchanged.
```

## What does not belong

- **Restating the diff.** "Changed `retry.ts` to check the status code" - the reader can see that.
- **Apologies or narration.** "Sorry, had to touch this file too", "as discussed in standup".
  Where context lives in a system the reader can link to, use a trailer or a URL instead of a story.
- **Aspirational claims.** "Fully fixes the timeout issue", "improves performance", "makes it more robust" -
  say what happens, or say what you observed and leave the conclusion out.
- **Anything that should be a separate commit.** A body that begins "Also…" is a smell ([`03`](03-atomicity-and-staging.md)).
- **Secrets, tokens, internal URLs with credentials in the path, personal data.** A commit message is
  replicated into every clone and often into public mirrors; deleting it later does not un-publish it.
- **AI co-authorship claims the project did not ask for, or "Generated by" lines pasted onto a human's
  work.** If the project has a convention for recording assistance, follow that convention; otherwise the
  commit is credited to its author, like anyone else's.

## Bullets and lists

Prose paragraphs are the default. Lists are justified when the content is genuinely enumerable - a set of
behavior changes in one commit, the steps of a migration, the measured numbers before and after. Keep them
short, one item per line, and do not make a list of things that belong in the diff or in a task tracker.
