# Project Structure

The standard NoF layout, as generated by `scripts/init-nof.sh`:

```
<project-name>/
├── index.html
├── js/
│   ├── router.js              # Navigo configuration and route table
│   ├── store.js                # Global state (van.state + van.derive)
│   ├── utils.js                 # renderToApp() + rendering helpers
│   ├── base/                    # Dumb, app-agnostic UI primitives
│   │   ├── Button.js
│   │   ├── Image.js
│   │   └── ...
│   └── components/              # Business components, built from base/
│       ├── LoginButton.js
│       ├── HeroImage.js
│       ├── ProductCard.js
│       ├── Modal.js
│       └── ...
├── pages/                       # Page definitions (HTML + script)
│   ├── home.html
│   ├── products.html
│   ├── cart.html
│   └── about.html
├── css/
│   └── style.css
└── README.md                    # Project-local notes on structure and running it
```

## What belongs where

- **`js/store.js`** — all global reactive state and the actions that
  mutate it (by reassignment, never in-place mutation). Anything more
  than one component needs to read or change belongs here, not scattered
  across component files. See `state_management.md`.
- **`js/router.js`** — the single Navigo instance and its route table.
  Only one router per app; don't instantiate Navigo more than once.
- **`js/utils.js`** — the small set of rendering helpers
  (`renderToApp`, `renderToAppWithProps`, `navigateTo`). Keep this file
  small and generic — page-specific logic doesn't belong here.
- **`js/base/`** — dumb, app-agnostic UI primitives (a styled `Button`,
  `Image`, `Input`). No business meaning, no store imports, would drop
  into any project unchanged. Introduced once a project has enough
  components that the same raw tag+class combo starts getting
  reimplemented in more than one of them — not needed upfront on a
  small project. See `components.md#base-vs-components`.
- **`js/components/`** — business components, generally built out of
  `js/base/` primitives rather than native tags directly. These carry
  app-specific meaning (`LoginButton`, `ProductCard`, `HeroImage`). A
  component that's only ever used on one page can still live here if
  it's a genuinely reusable unit; logic specific to assembling one page
  layout can live in that page's own script instead.
- **`pages/`** — one file per route. Each page is fetched via
  `fetch()` and its script executed on navigation (see `routing.md`).
  Pages compose components; they generally shouldn't contain component
  definitions themselves.
- **`css/style.css`** — plain CSS, no CSS-in-JS layer. Split into
  multiple files as the project grows if one file gets unwieldy, but
  don't introduce a CSS framework/preprocessor unless the person asks —
  that's outside NoF's minimal-dependency philosophy by default.

## Scaling the structure

Structure shifts as a project grows — splitting flat `components/` into
`base/` + `components/`, grouping `components/` by feature, splitting
`store.js` by domain, extracting route handlers out of `router.js` —
are trigger-based, not something to adopt upfront. See `code_health.md`
for the concrete triggers and before/after examples for each shift,
plus the code smells and hotspot files worth watching as a NoF project
grows.
